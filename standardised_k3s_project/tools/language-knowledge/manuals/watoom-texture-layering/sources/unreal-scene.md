# Dressing an Unreal landscape: creeks, scenery, water (verified on UE 5.8.4, 505 x 505 landscape, 2026-11-14)

Run these after the landscape, layer weights and material exist (`unreal_landscape_export.py`, `unreal_landscape_material.py`).
All three helpers are host-side Python (numpy + pillow) that write call lists for the `watoom-ue` tool; none of them talks to the editor.

## Order of work
1. Creeks first: `unreal_creeks.py` carves the heights and lays the water. Scenery placed before the carve ends up floating over the channel.
2. Scenery second: `unreal_scene_scatter.py` reads the weights, the heightmap and `creek_mask.u8` and writes the foliage, rock and village calls.
3. Look at a capture after each phase; a successful call is not a visual check.

## Creeks: unreal_creeks.py
The lowest lines of the terrain are found by filling depressions and accumulating D8 flow; the strongest channels from source to coast or map edge become creek paths.
`unreal_creeks.py --ue-dir ue --size-m 4000 --z0 3677.7 --raw-per-cm 4.4387 --landscape ZAS_Landscape --material /Game/AdvancedVillagePack/Materials/M_Inst_Water --out creek_calls.json`
`--landscape` (the landscape actor label, profile key `landscape`) is required and is written into every carve and paint call. `--material` must be a material that renders on a plain plane (profile key `plane_water_material`); the profile's `water_material` is the Water-plugin river material for `ue_place_river.py` and is never used here.
Get `--z0` and `--raw-per-cm` from `landscape.get_height_region` (`rawUnitsPerWorldCm`, and minZ against minRaw). The imported raw height equals the 16-bit PNG value, so the source PNG can be compared directly.
For a creek that reads as a real stream add `--depth-cm 450 --width-px 1.6 --bank-px 4.5 --irregular --bank-paint --baseline heightmap16_creeks.png --clean Creek_`: `--irregular` varies width, depth, bank slope and bank edge along the creek so it stops looking like a uniform ditch, `--bank-paint` splits the banks into sections of pebbles, sand, mud, stone and plain grass (it writes `creek_bank.u8` and `with_creeks/<layer>.u8`), `--baseline` limits the carve to tiles that differ from the heightmap already in the editor, and `--clean` deletes the previous water planes first.
Bank painting adds the layers `sand` and `stone` (`landscape.add_layer`) and writes every layer's weights over the touched tiles with `landscape.set_layer_weight_region`; the weights must sum to 1, so the script blends the new sections into the existing `<layer>.u8` weights instead of overwriting them, and rounds so every pixel sums to exactly 255 (the engine does not renormalise).
Phase `carve` is `landscape.set_height_region` tiles with `heightsBase64`; read a carved vertex back with `landscape.get_height_region` and compare it with `heightmap16_creeks.png`.
Phase `water` is `level.place_actor` of `/Engine/BasicShapes/Plane` segments with a water material, stepped down with the bed. No Water plugin is needed.
Water materials found in the owned packs, tested on flat planes in a scene render: `/Game/AdvancedVillagePack/Materials/M_Inst_Water` and `M_Water` render as pale, rippled, translucent water and are the ones to use; `/Game/Wildwood/Material/MI_River_01` (parent `MM_Water`, built for river splines) renders pure white on a plane; a plain translucent colour material works but is flat and worse than the pack water, so do not build one.
Placing 337 water segments: `level.place_actors_batch {actors:[{mesh, staticMesh, label, location, rotation, scale}]}` places 20-40 per call but ignores `material`, so set it afterwards for every segment with `level.bulk_set_component_property {componentName: "StaticMeshComponent0", propertyName: "OverrideMaterials", value: ["<material>.<material>"], labelPrefix: "Creek_"}` and switch the shadows off with `propertyName: "CastShadow", value: false` (plane water that casts shadows shows black wedges). `level.delete_actors {labelPrefix}` removes a set; labels must be unique, because a duplicate label makes every bulk write refuse ("Ambiguous actor selector"). A stopped batch can leave a half-placed set: delete by prefix and place again rather than guessing.
Continuous water: `--ribbon-mesh /Game/ZAS/Meshes/SM_CreekWaterPlane` (a copy of `/Engine/BasicShapes/Plane` made with `asset.duplicate`, its slot 0 set with `asset.set_mesh_material` to the water material) replaces the separate planes with one `level.create_spline_actor` plus `level.build_spline_meshes` section per 15 path points (phase `ribbon`; the `water` phase then only deletes the old `Creek_` planes). Apply with the `water` phase first, then `ribbon`. It removes the ragged joins; the pack water still looks pale and flat from the air, and a section whose spline cuts a tight bend runs straight across it.

Test a water material before spreading it: put one plane per candidate side by side near the ground, photograph them with `tools/rig-ue-mcp/ue_viewport_shot.py` (a material is judged in the real viewport, see "Seeing the scene"), delete the planes, then change all segments with `level.set_actor_material {actorLabel, materialPath, slotIndex}`.

## Scenery: unreal_scene_scatter.py
`unreal_scene_scatter.py --ue-dir ue --size-m 4000 --min-z <z of raw 0> --max-z <z of raw 65535> --recipe recipe.json --out scene_calls.json`
`--min-z` / `--max-z` are the world Z of raw height 0 and 65535: `z0` and `z0 + 65535 / raw_per_cm`. They equal the landscape bounds only on a freshly exported heightmap that was normalised to the terrain's own range; after a carve or with live heights use the `z0` form. The script takes only `size_m` from a `--project` profile (not `z0`, `raw_per_cm` or `sea_cm`). Every `.u8` file in `--ue-dir` and `--layers-dir` must be the heightmap's size: a file of another size is refused with both sizes in the error.
The recipe names meshes per kind: grass, trees, bushes, flowers, rocks, and optional village houses and props (Blueprint class paths ending in `_C`). Find real paths with `asset.search`; pack folders can nest.
Phases in order: create_types, type_settings, add_types_to_level, forest, rocks, village, flowers, grass. Run in batches of about 25 calls and save the level between phases.
Trees and bushes line the creek: `creek_trees` places them in a band outside the channel and bank (`creek_tree_count`, `creek_tree_band_px`, `creek_trees_per_call`), and `creek_rocks` puts rocks on the pebble and stone bank sections. Every `foliage.add_instances` call costs several seconds on a level that already holds a million grass instances, so put more instances in each call and fewer calls.
Trees, bushes and rocks use `AlignToNormal` false and a small negative `ZOffset`, because aligning to the slope tilts the trunk so one side floats and the other sinks.
Instances keep the transform they were placed with, so after changing a foliage type's settings remove its instances (`foliage.remove_type_from_level` with `force: true`) and place them again.
Foliage type settings are written with Unreal property names as text through `foliage.set_settings`, for example `AlignToNormal: "False"` and `ZOffset: "(Min=-15.0,Max=-5.0)"`.
Grass is scattered on a grid over every pixel whose grass weight is over 40 percent so that it covers most of the ground; a few sites leave the ground looking like a flat texture.
Grass meshes need a test at eye level: a material that uses landscape ground projection (Wildwood `SM_Grass_01`) renders black on a custom landscape. Village-pack grass patches rendered correctly. 2026-11-17: confirmed deeper on `SM_Grass_01` -- disabling Nanite does NOT fix it (the one instance that looked lit in every test was the foliage-selection highlight, not real shading, never actually confirmed working); `editor.set_buffer_visualization {"buffer":"BaseColor"}` shows the clumps are solid black even unlit, so it is a genuine material BaseColor-output defect, not a lighting/shadow/Lumen/distance-field issue, and a cold editor restart does not change it (rules out stale GPU/VSM cache too). Not worth debugging further into the pack's nested material functions over the MCP route. A loose GLB pack with ordinary (non-landscape-projected) materials -- e.g. `Realistic_Grass_Pack_For_Games_Free` (`asset.import_static_mesh`, 9 mesh variants `Object_4..Object_20`) -- renders correctly at every distance with no changes needed. Prefer any owned grass pack whose material does NOT use landscape ground projection; test one instance at ~30-40 m before scattering at scale.
A grass type needs a draw-distance limit (`CullDistance` max about 15000) so a million instances stay workable in the editor.

After an island: `unreal_scene_scatter.py --heights heightmap16_creeks.png --layers-dir with_creeks` reads the final heights and layer weights, keeps trees and grass off the sea, beach and cliff masks (`island_under.u8`, `island_beach.u8`, `island_cliff.u8`, written 0 or 255 by `unreal_island.py`), and adds two phases: `coast_rocks` (boulders on the cliff foot, the beach and the water edge, `coast_rock_count`) and `bank_pebbles` (small stones from the recipe's `pebbles` meshes, for example the StyleHex `SM_Stone_Pebble_1..3`, along every painted creek bank, `bank_pebble_count`).

## Seeing the scene: two tools with different jobs
One rule: use `tools/rig-ue-mcp/ue_viewport_shot.py OUT.png [--camera X Y Z PITCH YAW]` (the real editor viewport, pulled back from the rig) to judge LIGHTING, MATERIALS, post-process and colour; use `editor.capture_scene_png` only for geometry and placement. `editor.capture_screenshot` writes its file on the rig asynchronously (do not count on an inline image from it) and keeps returning the same frame when the editor is CPU-throttled or not repainting; the tool switches the throttle off, nudges the viewport, pulls the file back and restores the throttle. Whenever another line of this page or an older note names a capture call for a lighting, material or colour check, this rule wins.
`editor.capture_scene_png {outputPath, inline: 1600, width, height, location, rotation, fov}` renders through a transient camera, so it always shows the current level and a camera you choose; `outputPath` is required and the file is written on the rig. `warmupFrames` starts an asynchronous job (poll with `captureId`) and does not return an inline image, so omit it for an inline picture.
Do not use pitch -90 (the framing is lost); use pitch -35 to -60 from a height.

## Editor behaviour that fooled earlier captures
A viewport that is not repainting returns the same frame from `editor.capture_screenshot`; call `editor.set_realtime {enabled: true}` and `editor.redraw_viewport`, and compare two captures before trusting them.
`level.create` on an existing level path only reloads it when that level is already open; use `editor.open_asset` with the map path to switch to it.

## Ground texture: tiling and normals
Landscape `TexCoord[0]` is ONE UV UNIT PER LANDSCAPE QUAD (`quad_m = size_m / (vertices - 1)`, 7.94 m on a 4 km / 505 vertex map), not per component and not per map. So `tiling = quad_m / tile_m`: about 2.5 gives roughly 3 m tiles. A tiling of 70 repeats every 11 cm and a 4K texture averages to flat olive from any normal distance; 800 repeats every 1 cm. Measured on the test game (2026-11-16): 70 -> flat colour, 2.5 -> visible grain and mud patches.
`unreal_landscape_material.py --landscape LABEL --tiling 2.5 --detail 0.11 --normals LAYER=/Game/normal ...` multiplies each layer's colour by a second, larger-scale pass and adds the weighted normal maps; both cost texture samplers, so with more than about 5 layers they push the material over the sampler budget (see below) and `--macro` is the cheaper way to break up the flat look.
Pack landscape textures found: `/Game/AdvancedVillagePack/Textures/Landscape/T_Landscape_{Grass,Soil,Pebbles}_DH` with `_N` normals, and `/Game/Fantastic_Village_Pack/textures/T_ENV_TERRAIN_*_BC` with `_N`.
A newly assigned landscape material shows only after the level is saved and truly reloaded: open another level with `editor.open_asset` (a scratch level such as `/Game/Maps/L_Scratch`) and then the real level again. Reopening the same level path does not reload it, and the landscape keeps drawing the old look (or default grey), which made several material comparisons meaningless.
A landscape material has a texture sampler budget of 16 that the landscape shares with its own weightmaps and heightmap: a 7-layer material with a detail pass referenced 15 textures and rendered default grey, while the same 7 layers with one macro texture (8 textures) rendered correctly. Use `material.get_shader_stats` (`referencedTextureCount`) and keep it at about 8-10; drop the detail pass and the normal maps before dropping layers.
If the ground still reads as one saturated colour, add `--macro 0.006 --macro-gain 2.0` (and optionally `--macro-texture /Game/...`): the finished colour is multiplied by a DESATURATED texture sampled a few times across the whole map, so the ground gets light and dark patches over hundreds of metres. The macro factor is `repeats / ((vertices - 1) * tiling)`: 6 repeats across a 505 vertex map at tiling 2.5 is about 0.005, and 0.006 gives about 7.5; on the live material expression 28 `uvm` is set to 0.08. The macro texture must be desaturated: a brown soil colour multiplied into green grass turns the whole ground grey-brown.

## Scale: unreal_scale_fit.py
Packs use different scales; a stylised house was 18 m tall next to a 1.8 m human, and a wizard scaled 1.6 was 2.95 m tall.
Measure with `level.get_actor_bounds` (boxExtent is half the size) or `asset.get_mesh_bounds`, then run `unreal_scale_fit.py --measure measurements.json --out scales.json`; the targets use a 180 cm human (house 8 m, well 2.2 m, tree 15 m, bush 1.3 m, boulder 2.2 m, dragon boss 12 m).
Apply the scale with `level.move_actor {actorLabel, scale}` or the recipe keys `house_scale`, `prop_scale` and `foliage_scale` of `unreal_scene_scatter.py`, then snap to the ground again.

## Putting actors on the ground: unreal_ground_fit.py
`unreal_ground_fit.py --components building_components.json --ue-dir ue --heights heightmap16_creeks.png --size-m 4000 --z0 3677.7 --raw-per-cm 4.4387 --out ground_fit.json` puts buildings and props on the ground from real mesh bounds: the base of a building is its body / base / foundation meshes (not the lowest part, such as a barrel on a porch), the ground level is the mean landscape height under that footprint, the terrain under the footprint is flattened to it (a smooth pad), and the building is moved vertically with `level.batch_translate` so its base sits 2 cm into the pad.
Read the component bounds with `level.get_component_tree {actorLabel}` and a large output limit (a house tree is tens of kB; a truncated read silently returns no components), keep `boundsOrigin` and `boundsBoxExtent` of the StaticMeshComponents, run the `pad` phase, save, then the `move` phase, and measure again: after one pass buildings were within about 20 cm and a second small nudge finished the worst props.
On this map a landscape pixel is 7.9 m, so a pad is a terrace about 16 m wide; a hillside of 100-200 cm under a house cannot be matched by moving the house alone.
Actor-level bounds (`level.get_actor_bounds`) are not usable for this; they showed a house 1.2 m in the air as sitting correctly.

## Putting actors on the ground: snap_actor_to_floor
`level.snap_actor_to_floor {actorLabel, maxDistance}` drops an actor's lowest bounds point onto the first surface below it; run it after every rescale, because scaling moves the base.
`level.get_actor_bounds` includes lights, smoke and other components, so a bounds-bottom against the landscape height at the centre can report a building as buried or floating when the render shows it sitting correctly; judge contact from a scene render at ground level, and treat the numbers as a hint.
An actor with a camera boom or other large components reports inflated bounds and floats after a snap; place those from the landscape height (`landscape.get_height_region`, meanZ) plus the capsule half height.

## Island, mountain and ocean: unreal_island.py
`unreal_island.py --ue-dir ue --size-m 4000 --z0 3677.7 --raw-per-cm 4.4387 --seed 5 --ocean-material /Game/WaterMaterials/Materials/M_Ocean --landscape ZAS_Landscape --out island_calls.json` turns the heightmap into an island with a mountain: the world edge becomes a randomised coast (random harmonics plus a domain warp, clamped so land never reaches the map edge), the shore is a gentle concave beach on most of the coast and a steep raised cliff on `--cliff-arcs` random arcs, a mountain of `--mountain-cm` (default 9000) rises in the middle, and sand, rock and stone layer weights are written to `island_layers/` with every pixel summing to 1.
The phases are `carve` (height tiles that differ from `--baseline`), `paint` (`landscape.add_layer` for sand and stone plus the weight tiles) and `ocean` (one plane `--ocean-km` wide, default 30 km, at the sea level). The ocean plane must reach the horizon: with a 1.6 times map-sized plane the sky started at the edge of the island. Keep it inside the 20 km sky dome. After the island, run `unreal_creeks.py --heights heightmap16_island.png --layers-dir island_layers --sea-cm <sea_cm>`, clear the old scenery, scatter again and ground-fit the buildings; terrain changes invalidate every instance that was placed on the old ground.

## Lakes and rough banks
Lakes and rough banks: `unreal_creeks.py --lakes --lake-material /Game/WaterMaterials/Materials/M_Lake --rough` puts a lake of random radius (`--lake-px`) and depth (`--lake-depth-cm`) at the head of every creek that starts inside the map (at least 24 pixels from the edge and well above the sea), carves a bowl, paints mud inside and sand on the shore, and places a thin cylinder disc at the water level; `--rough` uses two-scale edge noise and interleaves neighbouring bank types so the banks are never straight lines. `--sea-cm` makes the sea end the creeks, and `--heights` and `--layers-dir` read the island files.

## Sky: unreal_sky.py
`unreal_sky.py --center 200000 200000 --nebula 02 --out sky_calls.json` makes a permanent nebula sky with a sun: it deletes the blue `SkyAtmosphere` actor, places the pack's `BP_Star_Dome` blueprint, scales the actor to 0.00004 (the dome mesh is about 500,000 km wide, past the far clip), overrides the dome component with `MI_Star_Nebula_01..05`, and makes the `SkyLight` Movable with intensity about 1.2 lit from a specified cubemap (`--sky-source cubemap`, the default: `SourceType` `SLS_SpecifiedCubemap`, `Cubemap` `/Engine/MapTemplates/Sky/DaylightAmbientCubemap.DaylightAmbientCubemap`, `bRealTimeCapture` false). The `DirectionalLight` stays as the light source.
Which sky light form applies: a captured-scene sky light (`--sky-source captured`: Movable + `recaptureSky`, or `bRealTimeCapture` true) only lights the level when the sky mesh's material has Is Sky set. The star dome is not Is-Sky, so its capture is black and gives no ambient; use the cubemap form with it. The cubemap fields were verified with `editor.set_property` on the component object path (`--sky-component-path "<level>:PersistentLevel.SkyLight_0.SkyLightComponent0"` emits that); without that flag the script writes them with `level.set_component_property {actorLabel, componentName:"SkyLightComponent0"}`, which is not yet verified on a sky light, so read `SourceType` back and check a shadowed surface with `ue_viewport_shot.py`.
Black grass blades and black tree undersides were not a grass material problem: the grass material is already two-sided, masked and shaded, and the sides facing away from the sun were black because the level's SkyLight was Static with no capture. `level.set_light_properties {actorLabel, intensity, mobility: "Movable", recaptureSky: true}` fixed it on the level that still had an Is-Sky sky; under the star dome the recapture is black again and the specified cubemap is the fix (previous paragraph). The first capture after changing the dome material can still be black while the 26 nebula textures stream in; capture twice.

## Starting the editor: ue_route.py ensure
Starting the editor without anyone opening it: `editor.start_editor` on the route launches the editor through the rig's `WatooM-UeEditorStart` task, but it stops waiting after about 150 s and then reports "the editor process is gone - it exited during startup" while the editor is still booting (a cold start took 12 minutes on 2026-11-14 and the bridge on port 63053 only appeared at the end). So call `project.get_status`; if `editorConnected` is not true, call `editor.start_editor` once, ignore its failure text, and poll `project.get_status` every 15 s until `editorConnected` is true. `tools/rig-ue-mcp/ue_route.py ensure --max-wait 1200` does exactly that from the lab server.

## Moving the village and characters (after the terrain changes)

When the terrain is regenerated the village may no longer sit on flat ground. Move it, do not rebuild it:

1. Take the target from `village_center` in the scatter recipe (`scene_calls4.json`), the flattest patch of the new heightmap. The offset is target minus the current well position (x, y only).
2. One call: `level.batch_translate {"offset": {...}, "actorLabels": [houses, well, campfire, cart, chest, zombies, weapons, player]}`.
3. Shift the `o.x` / `o.y` of every entry in `building_components.json` by the same offset (z stays), then run `unreal_ground_fit.py` against the heightmap that is in the editor. Landscape parameters: `z0 = landscape_z - 32768 * scale_z / 128`, `raw-per-cm = 128 / scale_z`, `size-m = scale_x * (n - 1) / 100`.
4. Run its phases `pad`, `move`, then move the characters and held weapons (they are not in the components file) by the dz of the nearest prop (the well). Save the level.
5. Re-run the scenery scatter so trees and rocks keep clear of the new centre; keep the machine load guard low (6) when the server is shared, so a bulk run cannot cause an OOM.

## Review lessons from the 2026-11-15 visual pass
- Review geometry and placement with `editor.capture_scene_png` (lighting, materials and colour: `ue_viewport_shot.py`; outputPath must be under the project's `Saved/`, e.g. `F:/Documents/Unreal Projects/WatooM_UEMCP_Test/Saved/Review/x.png`, `inline` returns the image) from several heights and yaw angles: village at ground level from two sides, top-down, coast from outside, and a wide oblique. One view hides most faults.
- **No ocean**: the ocean phase of `unreal_island.py` sent `mesh`, which `level.place_actor` rejects (it takes `staticMesh`); the failure was swallowed, so no plane existed. Fixed in the script. After running a phase, confirm the actor exists (`level.get_outliner {nameFilter:"Ocean"}`), not only that the call list finished.
- **Black sky**: the dome's `OverrideMaterials` ended up as the bare master `M_Star_Nebula` (all star and nebula intensities 0). Re-apply `level.bulk_set_component_property {labelPrefix:"ZAS_StarDome", componentName:"Dome", propertyName:"OverrideMaterials", value:["<mi>.<MI_Star_Nebula_02>"]}` after placing and scaling the dome, then read the dome's component tree or MID (`material.read_instance` on the MID path) to confirm a parent of `MI_Star_Nebula_NN`, and capture twice.
- **Floating buildings after the terrain changed**: `unreal_ground_fit.py` assumes its `--heights` png is what the editor holds. It was not (mean 73 raw units apart), so the pads did not flatten the real ground. Read the live region with `landscape.get_height_region` (it returns `heights` as a raw array and `rawUnitsPerWorldCm`), paste it into a copy of the png, and fit against that. Also shift the saved component bounds by any dz already applied. `level.line_trace` does not hit the landscape in the editor world, so use the height region, not traces, to check grounding.
- **Missing grass and rocks**: a chain script that treats the text "done N of M" as finished stops every phase after one time slice. Compare N to M and loop until they are equal.
- **Ocean looked like streaky white sheets**: `M_Ocean` (translucent, designed for the pack's own overview map) and `M_Ocean_Distance` / `M_Ocean_Radial` (invisible without their parameters) do not work on a plain 30 km plane. `M_Lake` renders as real water. Make an instance and tint it, then use it as `--ocean-material`: `material.create_instance {parentPath:"/Game/WaterMaterials/Materials/M_Lake", name:"MI_Sea", packagePath:"/Game/WaterMaterials/Materials"}`, then `material.set_parameter {assetPath, parameterName:"ColourDeep", parameterType:"vector", colour:{r:0,g:0.02,b:0.08,a:1}}`, `Colour` {0,0.07,0.16} (values like 0.3/0.45 come out as bright cyan), then `level.set_actor_material {actorLabel:"Ocean", materialPath:"/Game/WaterMaterials/Materials/MI_Sea", slotIndex:0}`. The sea plane also shows inland wherever the ground is below the sea level (creek lake bowls); that is expected.
- **Sea inland and no beach**: `scripts/unreal_coast.py` (tested) raises land that is below sea level + 150 cm and ramps the sand layer from the water line 10 pixels inland (not on cliffs), keeping every pixel's weights at 255. Feed it the LIVE heights (16 `landscape.get_height_region` tiles of 127 px pasted into a 505 x 505 png), `island_under.u8`, `island_cliff.u8` and the latest layer folder; run its `heights` then `paint` phases (84 tile calls for 7 layers) with a load guard, then save the level. The village ends up on the sand if it sits within 10 px of the coast.
- **Ground washed out to white when facing the dark sky, black when facing the sun**: auto exposure. Place a `PostProcessVolume` (`level.place_actor`), `level.set_volume_properties {properties:{bUnbound:true}}` and `level.set_fixed_exposure {exposure: 1.5}`; this tool's scale is not EV100 as expected, 12 and 9.5 were far too dark, about 2 balanced sky and ground. Check a view toward the sky and a view toward the ground after changing it.
- **Neon tree colour**: the lime comes from the leaf albedo. `Saturation`, `Color_intensity`, `Color Top` and `Color Lower` on the Wildwood `MI_Tree*_Leaves_*` instances changed it only slightly, and the `Colour Tint?!` static switch cannot be set with `material.set_parameter`. What worked is `level.set_post_process_settings {actorLabel:"ZAS_PostProcess", enableOverrides:true, settings:{ColorSaturation:{x:0.72,y:0.72,z:0.72,w:1}}}`.
- **Ground detail**: close up (3 m) the grass texture is fine; from 20 m the ground reads as soft brown/green blotches because layer weights are one pixel per 8 m. More grass and rock instances, not a different texture, give the mid-distance detail.

## Ocean, shoreline and rivers with the Water plugin (procedure; replaces the flat ocean plane)
Use the engine's Water plugin (already enabled in the rig project). A flat plane has right-angle edges where the sea recedes and cannot carve a shoreline; a `WaterBodyOcean` follows a spline and the Water edit layer shapes the shore.

1. Landscape edit layers: the first `WaterBodyOcean` makes Unreal open the modal "Insert New Landscape Edit Layer" dialog. The MCP route cannot press its button (refused: `dialogBlocking`), so the owner must click Complete in the editor. After it, the landscape has two edit layers, `Layer` (your heights) and `Water`. Check with `landscape.list_edit_layers`; read heights with `landscape.get_height_region` (merged) and `landscape.merge_edit_layers {updateNow:true}`.
2. A `WaterBodyOcean` placed at the origin has a tiny default spline and the ocean is everything OUTSIDE its loop, so its carve flattened the whole map to raw height 0. If a merged read suddenly returns 0 everywhere, delete the body (`level.delete_actor`), merge, and the heights come back (the base layer is untouched). Never leave a default ocean on a landscape.
3. Place it at the real sea level: `level.place_actor {actorClass:"WaterBodyOcean", label:"ZAS_Ocean", location:{x:0,y:0,z:<sea_cm>}}`.
4. Shape the coast: `level.set_spline_points` refuses water splines ("subclass metadata"). ## Deep creek channel, deep sea, and what actually draws the water (2026-11-15)
- **What you see may be the old ribbon, not the water body.** If `level.get_actor_details {actorLabel, includeProperties:true, propertyName:"WaterMaterial"}` says `None`, the pale water in a scene capture is the `CreekRibbon_*` plane actors, so carving deeper changes nothing you can see. Give the river body its materials (`level.set_water_body_property` for `WaterMaterial` = an instance of `Water_Material_River`, `WaterInfoMaterial`, `UnderwaterPostProcessMaterial`, `WaterHLODMaterial`), rebuild the zone (`level.rebuild_water_zone` takes the `WaterZone` actor path, not the river) and hide the ribbon with `level.set_editor_visibility {hidden:true, actorLabels:[...]}`. A scene capture (`editor.capture_scene_png`, async: call again with the returned `captureId` and `inline` of at least 16 pixels) does NOT draw the Water plugin's near water, so judge water only in the live viewport.
- **The ribbon can also be left live WITH real materials, not just invisible.** Found 2026-11-17: `CreekRibbon_*` plane actors from an earlier `unreal_creeks.py --ribbon-mesh` apply were still in the level (with the pack water material) after a later session added the Water-plugin `WaterBodyRiver` creeks on top -- two real, differently-shaded water surfaces stacked at the same transform (double refraction/colour visible in a live viewport, not caught by `WaterMaterial: None`). `level.get_actors_by_class {"labelPrefix":"CreekRibbon_"}` to check for survivors whenever a map already has both a `unreal_creeks.py` ribbon pass and later Water-plugin river actors; `level.delete_actor` each one once the river body is confirmed showing (do not just hide them -- delete, since the ribbon pass is not meant to coexist once the river exists).
- **Deep middle, shallow sides:** `unreal_creek_profile.py` carves the live heights along the creek spline: bed = water Z - `--deep-cm` x (1 - (s/half-width)^2)^1.5, so the centre is deepest and the sides shelve up to the water level, plus a low rim (`--berm-cm`) so the flat water cannot flood low ground beside it. One landscape pixel is about 8 m wide, so use a half-width of about 24 m (3 pixels); a real cross-section needs several pixels. Back up the live heights first, run `ue_run_phases.py calls.json` (load guard, stops at the first failed call), then `landscape.merge_edit_layers {updateNow:true}`, `level.rebuild_water_zone`, `level.save`. Set the water body `Depth` and `RiverWidth` curves to match (`editor.set_property` on `<actor>.WaterSplineMetadata`).
- **Trees at the edges, none in the deep middle:** after a carve, run `tools/rig-ue-mcp/ue_creek_foliage.py` (dry run first, then `--apply`): instances more than 150 cm under the water are removed, instances on shallow edges or banks are re-added at the new ground height (so trees can stand in the shallow edge water), the rest stay. Run it before anything else edits that foliage (indices only stay valid until then).
- **Sea floor:** an island heightmap leaves the whole sea as a flat plateau a few cm above the sea level, so the water is zero deep and never darkens. `unreal_ocean_depth.py` ramps the sea floor from the waterline down to `--deep-cm` over `--ramp-m` (100 m) and holds it, touching only sea connected to the map edge. The deepest possible floor is raw height 0 (`--z0`), 11 m under a sea at 4849 cm here. The ocean body's own brush flattens the sea back to the plateau, so set `bAffectsLandscape` false on it first (`level.set_water_body_property {actorLabel:"ZAS_Ocean", propertyName:"bAffectsLandscape", value:false}`), then merge the edit layers and read a sea pixel back.

For a texture check set `editor.set_cvars {"cvars":{"r.Streaming.FullyLoadUsedTextures":1}}` (session only, set it back to 0) and capture with `warmupFrames` 150; it did not change the terrain result here, but it rules streaming out in one call.
- A camera below the water surface shows a black void with the underside of the waves. Sea level is Z 4849.26 cm; the 3750 cm plateau east of the island is the deep sea floor. Keep captures of the sea and the shore above Z 4849, and check `landscape.get_height_at_point` first.
- A wide shot from 8 m up of a distant bank looks flat even when the texture is fine. Judge a ground texture from about 1.5 m above the ground (camera Z = `landscape.get_height_at_point` + 150) a few metres away, on dry land, not in a creek (the creek bed is underwater).
- Tiling of every landscape layer is `material.set_expression_value {materialPath, expressionIndex:0, uTiling, vTiling}` (expression 0 = `uv`, now 0.075 on the test map, down from an earlier 2.5); the macro-variation node `uvm` (logical `expressionIndex` 28 in `material.read_graph`/`list_expressions`, but object path `MaterialExpressionTextureCoordinate_1` for `editor.get_property`/`set_property` -- the two numbering schemes differ, UE names objects by creation order not graph position) tracks it at a fixed ~31.25:1 ratio (0.0024 now). The tiling WAS the flat look: at 70 every layer averaged to one colour.
- Tiling is a U-shaped problem, not monotonic: too high (70, ~11cm tiles) averages every layer flat from mip-mapping; too low (tried down to 0.0375, ~85m tiles) brings the SAME flatness back from the opposite direction (one tile covering a whole plateau, barely any variation) plus a repeating diamond-grid seam from the macro node once it drifts out of ratio with the base. Changing the base tiling without scaling the macro node by the same factor shows the seam even in the safe middle range. Judge a new value at both a close shot (1.5 m up) and a wide/aerial shot over a flat area (e.g. a levelled pad) -- the regression only shows at one of the two distances depending on direction. 0.075 base / 0.0024 macro (2026-11-17) is clean at both; re-check this if a wide aerial pass over flat ground starts looking pale again.
- Steep creek banks (ground rises ~4 m in 10 m) get vertical stripes from the planar landscape UV: give steep faces a rock/dirt layer or sample triplanar instead of stretching the grass layer.
- Layer weights at a spot: `landscape.get_layer_weight_region {layerName, actorLabel:"ZAS_Landscape", region:{minX,minY,maxX,maxY}}` returns `paintedFraction` per layer (vertex units, not cm).


## One project profile for any game (2026-11-16)
The per-game numbers are not hard-coded. Everything that differs per game (landscape actor label, `z0` and `raw_per_cm` height mapping, `size_m`, sea level, label prefix, content root, river material, rig Content folder) lives in one JSON profile: copy `templates/unreal_project.example.json`, fill it in and pass `--project FILE` (or `export UE_PROJECT=FILE`) to any `unreal_*.py` / `ue_*.py` / `rig_copy_pack.py`. It fills the matching flags (`--z0`, `--raw-per-cm`, `--size-m`, `--sea-z`/`--sea-cm`, `--landscape`, `--material`, `--prefix`, `--dest`, village `--type-dir`) and, when present, they stop being required; a flag on the command line still wins. A key only reaches a script that has the matching flag: `z0`, `raw_per_cm`, `size_m`, `sea_cm` and `landscape` reach every script with those flags (`unreal_scene_scatter.py` takes only `size_m`); `water_material` reaches only `ue_place_river.py --material`; `plane_water_material` only `unreal_creeks.py --material`; `label_prefix` only `unreal_village.py --prefix`; `content_root` only `ue_village_build.py` (foliage types under `<content_root>/Foliage/Village`); `rig_content_dir` only `rig_copy_pack.py --dest`. Still fixed in the scripts, not profile-driven: the labels `Creek_<n>_<k>`, `CreekRibbon_<n>_<k>`, `Lake_<n>` (`unreal_creeks.py`), `Ocean` (`unreal_island.py`), `Village_House_<n>` / `Village_Prop_<n>` (`unreal_scene_scatter.py`) and the layer names grass, dry_grass, dirt, mud, rock (`unreal_ground_paint.py`, `ue_ground_fetch.py`); a game that names them differently must edit those constants. Without a profile the flags are required, so nothing silently falls back to another game's values (the old `ZAS_Landscape`, sea level and `ZAS_*` labels defaults are gone; `unreal_sky.py` now defaults to UE's own `SkyAtmosphere`/`SkyLight`/`DirectionalLight` names). New helpers: `import ue_project`, call `ue_project.apply(ap, argv)` before `ap.parse_args(argv)` and read extra keys with `ue_project.get(key, default)`. The mesh lists inside a recipe (`creek_biomes`, village `layout`) are data: swap them for the packs your game owns; the village `layout` is one ringed-village template and takes the pack folder from `--mesh-dir`.


## Placement principles from professional write-ups (2026-11-16, from search excerpts, not full reads)
Sources: Guerrilla "GPU-Based Run-Time Procedural Placement in Horizon Zero Dawn" (GDC 2017, guerrilla-games.com), CD Projekt RED "Landscape Creation and Rendering in REDengine 3" (GDC 2014), 80.lv terrain and river breakdowns, the GameDev.net terrain texture splatting tutorial, World Creator river docs.
- **Rules from maps, with artist control.** Horizon places all vegetation from paintable 2D world-data maps (height, slope, distance to water, painted ecotope) through data-driven, deterministic rules, so a re-run gives the same result and an artist can override any area. Do the same: drive scatter from the layer weights and masks (`unreal_scene_scatter.py`), keep the seed fixed, and hand-place or paint exceptions instead of editing the rules per spot.
- **Ecotopes.** A habitat (wet bank, dry slope, dune, forest floor) decides which asset types appear and how dense; one biome per area with a fraction of strays reads as natural (this is `creek_biomes`).
- **Layers from slope and height.** Steep gives rock, flat low ground gives grass, below the waterline gives mud or rock; break every transition with two noise masks and use world-aligned blending with noise so one rock texture does not visibly repeat. Splat opacity maps are low resolution, so the noise breakup is what hides the grid.
- **Rivers.** Give a river a floodplain it could meander in plus a blend zone that fades into the surrounding terrain; wet mud and rounded rock at the bed, vegetation thinning toward the water.
- **Paint over the procedural result.** Pure rules fail at edges; keep a painted layer on top for fixes.

## Too bright: exposure, nebula, atmosphere, clouds and fog (2026-11-18, T-0027)
The owner found the scene "very bright" even after the leaf fix. Measured on the test game with five horizon captures from one spot (the owner's view and yaw 0/90/180/270 at pitch -8, `ue_viewport_shot.py --camera`), using the mean sRGB luminance of the lower part of each frame (the ground):
- **The cause was the exposure floor, not exposure pumping.** The PostProcessVolume's auto exposure range was 0.3..2.5 and it sat at 0.3, its brightest end, in every view: locking Min = Max at 0.3 gave the same numbers as auto. Locked values: 0.3 -> 135, 0.45 -> about 105, 0.6 -> 86, 1.0 -> 59, 1.6 -> 40; HIGHER IS DARKER. Locked at 0.45. Views that face the sun stay darker (about 65) because they see the shaded side of everything; that is real backlight, not exposure. Set it with `level.set_post_process_settings {actorLabel, enableOverrides:true, settings:{AutoExposureMinBrightness, AutoExposureMaxBrightness}}`; `level.set_component_property` cannot reach post-process settings (they are on the volume actor, not a component).
- **Exposure compensation (bias) is logarithmic:** -0.7 made the scene far too dark (frame mean 161 -> 50). Use the locked range, not the bias, to set the level.
- **The nebula `Power` is an exponent: LOWER IS BRIGHTER.** On `MI_Star_Nebula_02`, `Power` 0.4 blew out 71% of the sun-side sky, 0.7 (the old value) 38%, 1.4 18%. `Power` and `Power_Extra_Cubemap` are 1.4 now.
- **Never change the dome's blueprint variables or move the dome.** `BP_Star_Dome` has `Brightness`, tint and cubemap variables that its construction script writes into the dome material. Setting one with `editor.set_property` and then `level.move_actor` in place (to rerun the construction script) replaced the `MI_Star_Nebula_02` override with `MID_M_Star_Nebula_0`, a dynamic instance of the black base material, so the sky went black again. That is the same fault that brought the pale leaves back. Change the look on the MI asset with `material.set_parameter`; put the override back with `unreal_sky.py`'s single `OverrideMaterials` call whenever anything touched the dome; check with `ue_look_check.py`.
- **Clouds need a SkyAtmosphere.** A `VolumetricCloud` alone rendered (seen looking straight up) but flat and grey, and the dark parts of the nebula stayed pure black. With a `SkyAtmosphere` the clouds are lit like real clouds and the black sky turns blue. Its distance haze tints the 20 km dome: at the default `AerialPespectiveViewDistanceScale` 1.0 the nebula almost disappears behind a plain blue day sky; at 0.35 the bright nebula still shows and the black parts are filled.
- **Cloud layer and material.** The default layer (`LayerBottomAltitude` 5, `LayerHeight` 10, in km) sits behind the 20 km dome near the horizon, so horizon views showed no clouds; 1 km bottom and 2 km height show them. Coverage is `Cloud_GlobalCoverage` on a project instance `/Game/ZAS/Sky/MI_ZAS_Clouds` of `/Engine/EngineSky/VolumetricClouds/m_SimpleVolumetricCloud_Inst` (engine default -0.2 is nearly clear; 0.35 now). This engine version names the parameters `Cloud_GlobalCoverage` and `Cloud_GlobalDensity`, not the `Layout_GlobalCoverage` of Epic's page; read them with `material.read_instance`. `StormClouds` is there for a later weather pass.
- **Cloud shadows on the ground did not work on this level.** The sun (`ZAS_Sun`, Movable, `bAtmosphereSunLight` true) has `bCastCloudShadows` true, `CloudShadowOnSurfaceStrength` 1, but a top-down A/B with the flag on and off showed no difference (0.1% of pixels). Open item.
- **Height fog:** `ExponentialHeightFog` at sea level, `FogDensity` 0.01 (default 0.02 is heavier), `StartDistance` 3000 cm so the foreground stays clear. Its component is `HeightFogComponent0`.
- **Weather is not done (open item).** A storm test (`Cloud_GlobalCoverage` 1.0, `StormClouds` 1, sun 1.2, `FogDensity` 0.035) dimmed the light but the sky still showed scattered clouds, not an overcast storm; the cloud amount needs more than coverage (try `Cloud_GlobalDensity` and the `Layout_CloudType` channels next). Rain needs a rain particle system and a shared wetness value that every material reads (a material parameter collection); the owned asset library has no rain or weather pack. Put the clear settings back afterwards: `StormClouds` 0, sun 3.2, then `unreal_atmosphere.py` and `ue_look_check.py`.
- **Selected actors show in captures:** a newly placed actor stays selected and its gizmo appears in `ue_viewport_shot.py` pictures; clear it with `level.epic_select_actors {actors:[]}`.
- **Tool:** `scripts/unreal_atmosphere.py --out atmo.json` writes all of it as phases (exposure, nebula, atmosphere, clouds, fog, then the dome override and `level.save` LAST); apply with `ue_run_phases.py atmo.json`; it is idempotent (`onConflict: skip`). Result on the test game: ground about 105 in every non-backlit view, the sun-side sky 18% clipped instead of 38%, no black sky. `ue_look_check.py` checks every value (29 checks).


## The look pass on any game (2026-11-18)
The look pass is generic; only the numbers are per game. For a new game:
1. Profile (`templates/unreal_project.example.json`): `label_prefix` (actor labels become <prefix>PostProcess, <prefix>Sun, <prefix>Atmosphere, <prefix>Clouds, <prefix>HeightFog), `content_root` (the cloud material goes to <content_root>/Sky), `sea_cm` (fog height), `size_m` (new actors go to the map centre), and optionally `post_process_label`, `sun_label`, `sky_dome_label` when the labels differ. A game without the nebula star dome sets `sky_dome_label` to "" (or passes `--dome ''`): no nebula or dome calls, and the atmosphere keeps its full distance haze (1.0).
2. Measure the exposure: `tools/rig-ue-mcp/ue_look_probe.py --out-dir DIR --sweep-exposure 0.3 0.45 0.6 0.8 --post-process <label>` captures the owner's view and four horizon views per value, prints the ground and sky numbers, restores the original exposure and the camera, and names the value closest to `--target` (105 on the test game). Look at the pictures as well, then put the value in the profile's `exposure`. Do not copy 0.45: it fits the test game's sun 3.2 and sky light 0.9 only.
3. `scripts/unreal_atmosphere.py --out atmo.json --project game.json`, then `ue_run_phases.py atmo.json`.
4. `tools/rig-ue-mcp/ue_look_check.py --from-calls atmo.json` (add `--from-calls` for every other look calls file the game applied). It turns every value those calls set into a check, resolves actors by label, and exits 1 on drift, so it works on any level whatever its object names. Run it again after every editor crash, restart or `level.load`.
What stays specific: the nebula steps assume the Animated Nebulas pack's `BP_Star_Dome` and `MI_Star_Nebula_*`; the cloud material is the engine's simple volumetric cloud; the `ue_look_check.py` defaults without `--from-calls` are the test game's object names.


## End to end: order, checks and what to do on failure (2026-11-17)
This is the order the tools above run in for one level. Do not start a step until the check of the step before it passed. The tool behaviour described here is covered by unit tests with a fake route; the sequence as one uninterrupted run on the rig is NOT verified, each part was run separately on the test game.
0. Before anything: `ue_route.py ensure`; write the project profile (`templates/unreal_project.example.json`: landscape label, `z0`, `raw_per_cm`, `size_m`, `sea_cm`) and pass `--project` everywhere; write the asset catalog (`references/asset-placement.md`). Keep every calls json, heights png and backup in the task's artifact folder.
1. Terrain and layers: `unreal_landscape_export.py heightmap` and `weights`, then create, import and paint (SKILL.md steps 1 to 4). Check: `landscape.get_height_region` and `get_layer_weight_region` of one tile equal the source.
2. Material: `unreal_landscape_material.py --landscape LABEL --tiling 2.5` (add `--macro 0.006` for a flat-looking ground), run its calls, then the reload recipe (`asset.save_all_dirty`, `level.load` another map, `level.load` this map, `editor.get_shader_compile_status {waitUntilIdle:true}`). Check: `editor.get_log` has no `Failed to compile Material`, `material.get_shader_stats` `referencedTextureCount` is about 8 to 10, and a `ue_viewport_shot.py` picture from 1.5 m above dry ground shows the layers.
3. Sky and light: `unreal_sky.py` (cubemap sky light by default), then `unreal_atmosphere.py` (locked exposure, dimmer nebula, weak atmosphere, clouds, fog; see "Too bright: exposure, nebula, atmosphere, clouds and fog"). Check with `ue_viewport_shot.py`: shadows are about a third to half of the lit brightness, not black; fix exposure and fill before any texture work. Then `tools/rig-ue-mcp/ue_look_check.py` must report 0 drift.
4. Shape the land, each from the LIVE heights (`ue_heights_fetch.py`, keep a backup copy): `unreal_island.py`, `unreal_coast.py`, then creeks and lakes (`unreal_creeks.py`, or `unreal_creek_river.py` / `unreal_creek_extend.py` / `unreal_creek_profile.py`), then `unreal_ocean_depth.py`. Apply each calls json with `ue_run_phases.py`, then `landscape.merge_edit_layers {updateNow:true}`, `level.rebuild_water_zone`, `level.save`. Check: read one changed tile back and compare with the script's output png; confirm the water actors exist (`level.get_outliner`); judge water only in the viewport. Round lakes: `ue_lake_as_waterbody.py`, then `ue_lake_check.py` and `ue_viewport_shot.py --around` (see the lake section at the end). Last in this step, once every creek and lake exists: berms, `ue_water_fetch.py` then `unreal_water_berms.py`, applied with `ue_run_phases.py` (see the berm section at the end), then `ue_creek_foliage.py` over every creek and lake.
5. Ground paint: `ue_ground_fetch.py`, `unreal_ground_paint.py plan`, `ue_run_phases.py`. Check: `get_layer_weight_region` of a steep bank shows rock and dirt.
6. Village pad and buildings: `unreal_village.py plan`, apply the pad, `ue_village_build.py --apply`, `unreal_ground_fit.py` for existing buildings. Check: a ground-level `editor.capture_scene_png` from two sides (placement is what scene captures are for).
7. Scenery last: refresh the heights, build the masks at the heights size, `unreal_scene_scatter.py`, run the phases in order with a small trial first. Then audit: `ue_foliage_census.py --catalog`, `ue_foliage_buried.py` (dry run, then `--apply`), `ue_foliage_buried.py --in-sea`, `ue_stray_check.py` (floating/sky and off-map foliage and placed actors, not just buried/sea). Check: the census lists no unclassified family and no contradiction; a rescan finds 0.
8. Save (`level.save`, `asset.save_all_dirty`) and record what was done, with the pictures, in the ticket.

On failure:
- A tool that exits non-zero has NOT finished. `ue_route.py call` exits 1 when any reply is an error (the MCP error flag, `"success": false`, an `error` field or text starting with `Error`); `ue_run_phases.py` stops at the first failed call and prints `rerun with --start N`: fix the cause, then rerun with that `--start`, do not start from 0 (earlier calls already ran).
- `ue_place_assets.py` and `ue_village_build.py` do not save when a step failed (exit 1, `NOT saving`). The level is changed but unsaved: fix the cause and rerun (`ue_place_assets.py` is re-runnable; `ue_village_build.py` is not, because the existing actors were already moved and their height above the old ground would be computed wrong, so reload the level without saving first), or pass `--force-save` only when the partial state is wanted.
- `ue_creek_foliage.py --apply` writes a receipt of every instance it removes first (`--out-removed`), stops at the first failed removal and re-adds nothing for it; run the dry run again before another `--apply`, the instance indices have shifted. It re-adds in batches of `--add-batch` (200), but on the rig every `foliage.add_instances` call now crashes the editor, whatever the batch size (see the berm section): do not run `--apply` until a one-instance add on a blank map survives. `ue_foliage_buried.py --apply` reports each failed removal and exits 1; rerun the dry run to see what is left.
- A material edit that "did nothing": `editor.get_log` for `Failed to compile` first, then the reload recipe, before changing anything else.
- A picture that did not change: for light, material or colour it must come from `ue_viewport_shot.py`. It gets the image inline over the normal route; if that fails too, the editor is not rendering (the scp fallback needs the `migrate` account, which is the owner's; do not work around it).
- Terrain went wrong: restore the backup heights with the calls from `unreal_creek_profile.calls_for(live, backup, landscape)` and `ue_run_phases.py`, merge the edit layers, and read a tile back before trying again.
- Anything that needs a dialog click, a plugin, an editor restart or an account on the rig is the owner's action: stop and ask.

## Stray placements, and smoothing sharp lake edges (2026-11-17)
`tools/rig-ue-mcp/ue_stray_check.py` finds foliage AND placed StaticMeshActor/SkeletalMeshActor level actors that ended up somewhere visually wrong: floating high above the ground or sea surface ("sky", usually a failed ground trace), fully submerged below the sea ("ocean"), or far below the ground ("buried"); also reports "off-map" (bounds centre outside the landscape) and "no-bounds" (empty mesh). Unlike `ue_foliage_buried.py` (foliage only, buried/in-sea only), this covers the floating case and non-foliage actors too, reusing `ue_foliage_buried`'s ground/sea maths rather than duplicating it. Read-only by default; `--apply` removes stray foliage instances and re-seats a sky/buried actor onto the ground, but never deletes an actor (an "ocean" or "off-map" actor has no safe automatic fix and is report-only). Flat water actors (`Lake_`, `Creek_`, `CreekRibbon_`, `Ocean`) are skipped by default since a `Lake_` disc legitimately hangs well above its carved bowl. Live dry run on the test level (2026-11-17, T-0055): about 17 minutes for 814,469 foliage instances and actors, 23,047 strays (23,037 sky, 10 buried), exit 0, so give it a timeout of at least 30 minutes; the `--apply` path has not been run live.

`unreal_lake_smooth.py` softens the sharp angles a carved lake shoreline can have: a feathered smoothing band around the waterline (reusing `box`/`grow` from `unreal_scene_scatter.py`, `dist_to` from `unreal_coast.py`, `calls_for` from `unreal_creek_profile.py`), blended to nothing outside the band so the lake's own depth and shape, and the rest of the terrain, are not otherwise touched. Lakes are given explicitly (`--lake x,y,z,radius_m` or `--lakes FILE`, including `unreal_creeks.py --lakes`' own output json directly) rather than auto-detected from pixel heights, because `unreal_creeks.py` sets a lake's water level from the 25th percentile of its ring heights, so a lake on sloped ground has ground below its own water level outside the bowl too -- a height threshold alone cannot tell lake from hillside there. Defaults (24 m band, 2 passes) are only tuned on synthetic test data; expect to adjust `--band-m`/`--passes` on a real map, and re-seat any foliage near the shore afterwards with `ue_stray_check.py` or `ue_foliage_buried.py`. A bank berm or an outlet creek's bank inside the smoothing band gets softened too, not just the lake-to-land edge. Run live twice next to Lake_3 (2026-11-18): the "cliff" it was meant to soften was really a sunken lake bed, a 24 m band barely changed it, and its calls, written into the base `Layer` while the lakes' Water offsets were still there, sank the carved beds in the rewritten tiles again. `ue_run_phases.py` now subtracts the Water offset; still run `ue_lake_check.py` on the lake first and fix any finding before smoothing (see the lake section below).

## Lakes as WaterBodyLake, and repairing a lake bed (2026-11-18, T-0049, replaces the 2026-11-17 WaterBodyRiver advice)
Use `tools/rig-ue-mcp/ue_lake_as_waterbody.py` for a round lake. Do NOT use a closed-loop `WaterBodyRiver` with a wide `RiverWidth` (the old `ue_lake_as_river.py` recipe): for a single closed spline, filling the middle by width floods the outside by the same distance, and live it put the forest under water. A `WaterBodyLake`'s closed spline IS the fill; it has no width.

**No visible water after placing a WaterBodyLake: move the actor.** A lake's water height follows the actor's own root Z, not the spline point Z. After writing the spline, call `level.move_actor` on the lake to `{x:0, y:0, z:water_z}`; that move runs the construction script that syncs the water. Without it the lake saves fine and renders nothing. This is what an earlier note blamed on a "WaterZone-registration bug".

**The landscape has two edit layers and the Water layer adds.** `Layer` (index 0) holds absolute heights; `Water` (index 1) is added on top: merged_raw = clamp(base_raw + (water_raw - 32768), 0, 65535). 32768 is the neutral value: writing it is a no-op. `landscape.set_height_region` and `get_height_region` with no `editLayer` write the base `Layer` and read the merged (visible) height. To make a vertex end at target_raw through the Water layer, write the change on top of its current Water value: water_raw + (target_raw - merged_raw). Writing the target height itself into the Water layer counts the base twice and drags the whole written rectangle towards raw 0, which shows as a lake bed at sea level and a square pit at the edge of the written rectangle.

**Trust the merged read; the base `Layer` read is wrong on whole lines.** On flat untouched ground with a neutral Water layer, the merged read gave raw 318 at x=126,y=40 and x=60,y=126, but `editLayer:"Layer"` gave 32549 and 53850 there; the whole x=126 and y=126 lines read up to 125 m off, while x/y = 127, 252 and 378 agreed. The rendered terrain matches the merged read. Never build heights from an `editLayer:"Layer"` read: `carve_lake_bank()`, `ue_lake_check.py` and `ue_heights_fetch.py` use the merged read and the Water read only. An earlier note on this page said the merged read was "stale inside a water body"; every scan behind it ran along y=126, so it was this fault. It is a read fault, not bad stored data: after the berm writes through `ue_run_phases.py` covered row y=126 for x 127-380, the merged read there matched the plan exactly, yet `Layer + (Water - 32768)` still disagreed with merged at 198 of those 254 vertices, while rows and columns 124, 125, 127 and 128 agreed (2026-11-18). Nothing needs repairing on those lines.

**A lake drawn as a flat square plane, lower than or apart from the creek, is a sunken rectangle of terrain under it.** A lake's water tiles always reach a little past its circle; the ground normally hides that. On Lake_3 and Lake_4 a rectangle the size of the carve region had sunk 20 m or more, with vertical walls, so the hidden tiles showed as a stepped square. The WaterZone was healthy (`level.get_water_state` listed all four lakes), so `level.rebuild_water_zone`, a move nudge or deleting and recreating the lake cannot fix it; fix the terrain. Lake_1 and Lake_2 were never broken: the "glassy top" on them was their old disc showing again (see below).

**A carve that reports "0 of N vertices changed" is not proof of a clean bed.** The carve keeps any vertex that is already below its target, so a bed already pulled to raw 0 by an old bad write is kept as it is. Check every lake with `tools/rig-ue-mcp/ue_lake_check.py` (read-only): it reports sea_clamp (raw 0 in the bed), water_outside_ring (Water values that are not neutral outside the bank ring), seam (a height step at the carve rectangle's border much larger than the steps just outside it) and dry_inside (ground above the water inside the circle), and exits 1 when it finds one.

**Repairing a bad bed.** When the base terrain itself sank (sea_clamp or seam with a neutral Water layer), restore the base from a heights png fetched before the lake work, only inside the carve rectangle and only where it differs by more than 1 m, with the Water layer neutral there; then carve again. That repaired Lake_3 and Lake_4 from the 2026-11-17 17:43 heightmap, with a backup of every vertex written first. When only the Water layer is bad, `ue_lake_as_waterbody.py --carve-only --clear-water-first` writes 32768 over the carve rectangle's Water layer, carves again and saves without touching the water body. `--recreate` deletes the water body and places a fresh one.

**Where the sunken rectangles came from: base writes that counted the Water offset twice.** `unreal_lake_smooth.py` and the other terrain helpers emit `set_height_region` calls without an `editLayer`, built from the visible heights, and rewrite whole 127-vertex tiles. Two smoothing runs next to Lake_3 (09:01 and 09:06) wrote visible heights into the base `Layer` while the Water layer still held the lakes' carve offsets, so every carved vertex in those tiles sank by its offset again. A later "restore" from base reads taken after that wrote the pits back.

**Every base-layer height write goes through `ue_run_phases.py`, which subtracts the Water offset (since 2026-11-18).** All the terrain helpers (`unreal_coast.py`, `unreal_creek_profile.py`, `unreal_ocean_depth.py`, `unreal_island.py`, `unreal_creeks.py`, `unreal_lake_smooth.py`, `unreal_ground_fit.py` pads) compute visible heights and emit `set_height_region` calls without an `editLayer`, which land in the base `Layer`. Before each such call `ue_run_phases.py` now reads the Water layer of the same tile and writes base = height - (water - 32768), so a carved lake bed inside a rewritten tile is not carved a second time. `ue_heights_fetch.py` writes the merged read into the png and prints how many vertices carry a Water offset. Apply height calls only with `ue_run_phases.py`; `--no-water-compensation` is for a calls json that really holds base heights.

**Water spilling past the circle near a creek mouth.** Where the original ground beyond the bank is below the lake surface (Lake_4 west side: ground 7217 against water 8798; Lake_3 north and east: 8168 against 8860), the water shows past the circle. The carve only lowers ground, so it cannot fix this: lower the lake's water height to its rim or creek-mouth level, or raise a rim except where the creek enters. The owner chose rims: `unreal_water_berms.py` builds them along every creek and around every lake (see the berm section below).

**Judge a lake from several angles and distances.** One camera angle showed Lake_3 as a clean round lake; the owner's own camera showed its water as a stepped square over a pit. Use `ue_viewport_shot.py OUT.png --around X Y WATER_Z RADIUS_CM`: it captures the owner's current view first, then top, four compass, close-low and far views, and puts the owner's view back. The tool asks `editor.capture_screenshot` for the image inline over the normal route; the `scp` pull from the `migrate` account is only a fallback.

**Hidden old discs come back on every level reload.** `level.set_editor_visibility {hidden:true}` only sets the temporary editor flag (`bHiddenEdTemporary`), which is not saved: after opening an autosave and coming back, the old `Lake_<n>` cylinders showed again as a flat glassy surface over the lakes. `ue_lake_as_waterbody.py --old-label` re-hides on every run; delete them with `--delete-old` once the owner has approved the lakes (`--materials-only --old-label Lake_<n> --delete-old` does only that, plus the materials; all four were deleted this way on 2026-11-18). A forced reload has also wiped a cylinder's `OverrideMaterials` before.

**Lake material.** Lake_1 and Lake_2 use `/Game/ZAS/Water/MI_ZAS_River.MI_ZAS_River` (translucent, rippled, the creek's own look); `MI_ZAS_Lake` renders flat, opaque and glassy. Give every lake the same material as the creeks unless the owner asks otherwise; the owner confirmed it ("creek water is better", 2026-11-18) and all four lakes now use it. To switch an existing lake use `ue_lake_as_waterbody.py --materials-only` (materials and properties only: no spline rewrite, no move, no carve).

Keep the lake spline a uniform circle (`circle_spline_text`): a spline fitted to the organic shore showed a crease at the point-0 wrap, and `bClosedLoop` writes do not take. Fit the shape on the landscape with the carve instead. Recipe per lake: `ue_lake_as_waterbody.py --label ZAS_LakeBody_<n> --center-x X --center-y Y --water-z Z --radius-cm R --material /Game/ZAS/Water/MI_ZAS_River.MI_ZAS_River --old-label Lake_<n>`, then `ue_lake_check.py --lake ZAS_LakeBody_<n>,X,Y,Z,R`, then `ue_viewport_shot.py --around`. Add `--delete-old` only after the captures look right. Then build the berms (next section).

## Berms along creeks and around lakes (2026-11-18, T-0049)
A creek or lake surface is flat at its water level, and the Water plugin draws it a little past its shape (each body's `ShapeDilation` is 4096 cm here and the water mesh tiles are 24 m). The ground is what hides that overhang: wherever the ground just outside a body is below its water, the water shows there as a stepped sheet past the shape. A carve only lowers ground, so berms are built as a separate step, after every creek and lake exists:

1. `tools/rig-ue-mcp/ue_water_fetch.py --out water.json` (read-only): every `WaterBodyRiver` (spline points with their water level, and the `RiverWidth` curve read from the body's `WaterSplineMetadata` with `editor.get_property`), every `WaterBodyLake` (centre, radius and water level from its circle spline; the `lakes` list is also a `ue_lake_check.py --lakes` file) and the sea level (the ocean actor's Z).
2. `ue_heights_fetch.py` for the live heights; keep the png as the backup.
3. `scripts/unreal_water_berms.py --heights live.png --water water.json --out berm_calls.json --out-heights berm.png --report berm_report.json` (plus `--project` or `--z0/--raw-per-cm/--size-m`). For every point outside a body's water edge (a creek: half its `RiverWidth` from the spline; a lake: its radius plus the carved bank, so the carve's underwater shore stays) it sets a crest of water level + `--crest-cm` (60) for `--crest-m` (24 m, one water-mesh tile), then an outer slope of `--slope` (0.5) down to the natural ground. It only raises ground, never inside any water body (so creek mouths, junctions and lake outlets stay open), never on ground below the sea, and caps each raise at `--max-raise-m` (20); a capped point is listed in the report and the exit code is 1 (lower that body's water there instead).
4. Look at the plan before applying: render the raise over the terrain. The first live plan built a 13 m berm out into the ocean around Creek_2's mouth, because the creek's last stretch was a few cm above the sea; that is why ground below the sea is now never raised.
5. Apply with `ue_run_phases.py berm_calls.json` only (it keeps the lakes' carved beds), `level.save`, then fetch the heights again and compare with the plan png (live run: 871 vertices raised, the rest unchanged, live equal to the plan), `ue_lake_check.py --lakes`, and `ue_viewport_shot.py --around` on the lakes with the biggest raises.
6. Refit the foliage: `ue_creek_foliage.py` with every `--lake` and `--spline` from water.json, `--reach-m` and `--lake-rim-m` wide enough to cover the berms (70 and 60 here), dry run first. Plants on a raised berm are buried and plants in the water stand in it.

Live result (2026-11-18): Creek_1 221 vertices (highest raise 4.3 m), Creek_2 258 (5.8 m), Creek_3 103 (1.5 m), Creek_4 104 (10.3 m, next to its sea mouth), Lake_1 135 (9.0 m, its low south-west side), Lake_2 3, Lake_4 47 (9.2 m); none capped. Lake_1 and Lake_4 were captured from eight views afterwards with the water held inside their circles.

**A foliage re-add of thousands of instances in one call crashes the editor.** The first `ue_creek_foliage.py --apply` after the berms removed 3615 instances of one type and re-added 2031 in one `foliage.add_instances` call: the bridge timed out after 30 s and the editor crashed inside `AddFoliageInstances` (`editor.get_engine_state`: phase crashed). The removal had not been saved, so the saved level was unchanged. The driver now writes a removal receipt first and re-adds in batches of `--add-batch` (200). **Batching did not fix it:** the rerun crashed on its first 200-instance batch, and one-instance adds then crashed the editor too, every time, with explicit transforms or center/radius/count, with `projectToGround` true or false, for a 142k-instance type and a 12-instance type, beside a lake and far from water, and on the blank `/Temp/Untitled_1` startup map (six crashes, 2026-11-18). The fault is in the rig's bridge plugin or engine (`FFoliageHandlers::AddFoliageInstances`, FoliageHandlers_Placement.cpp:539, into Foliage.dll), not in the level or the driver, and the plugin source is only on the rig. `editor.list_crashes` and `editor.get_crash_info` find the reports, but get_crash_info returns only the first 50 KB of the log, so the exception line is not readable through the route. **Cause found and fixed (T-0061, 2026-11-19):** the experimental `MeshPartitionWater` plugin. With it enabled every foliage add crashes, by the bridge and by Python `InstancedFoliageActor.add_instances` alike, for any type on any level; bisected on the rig, disabling only that plugin makes adds work (a 200-instance scatter, no crash), and no project content uses it. It stays disabled through `tools/rig-ue-mcp/project_plugins.json` + `rig_project_plugins.py --apply` (editor stopped). If adds crash again, first run `rig_project_plugins.py` (dry run) to see whether the .uproject drifted. After a crash: `ue_route.py ensure` (the editor reopens on `/Temp/Untitled_1`), `level.load` the map, then run the dry run again before another `--apply`.
