# Creation Studio

A standalone web page and JSON API for image and 3D-mesh generation, separate from Model Manager (which stays
focused on download/remove/activate of models). Stdlib-only Python, same shape as `tools/moss-image`: a host
service bound to the k3s cni0 bridge, a Glance IngressRoute, a self-contained web page, and offline tests with
fakes. This service owns **no** generation backend of its own — it only proxies to two existing services and
reads one existing read-only status file.

## Layout

| Path | What |
| --- | --- |
| `creation_studio_service.py` | stdlib-only service: static page, SDXL proxy, MOSS proxy, Mesh bridge proxy + GPU status |
| `web/index.html` | the page: four pipeline sections (SDXL, MOSS Image Studio, Mesh, GLB 3D Coder), each with its own prompt box, submit, progress/result, and a written "best prompts" reference block |
| `tests/` | offline tests using `tests/fakes.py` (fake Model Manager + fake MOSS HTTP backends); no GPU, no live network |

Run the tests: `python3 -I -m unittest discover -s tools/creation-studio/tests`

## The four pipelines

1. **SDXL** (base checkpoint, the installed NSFW-3D checkpoint, and the `thejagstudio/3d-animation-style-sdxl`
   LoRA) is generated by **proxying to the existing Model Manager HTTP API**
   (`tools/model-manager/server.py`). `ModelManagerClient` authenticates the same way an operator's browser
   does — `POST {prefix}/login` with the password read from `/data/ai/private/model-manager/password` (same
   convention as `manage.py`'s `validate()`), capture the `mm_session` cookie, `GET {prefix}/api/session` for a
   CSRF token, then call the existing `/api/generate`, `/api/jobs`, `/api/result`, `/api/models` endpoints with
   that cookie + `X-CSRF-Token` + matching `Origin` header. No GPU/broker logic is reimplemented; a 401/403 from
   Model Manager triggers exactly one re-login retry. Model Manager's own `/api/generate` only forwards
   `id`/`revision`/`prompt` today (its `settings`/`negative_prompt` support exists in `operations.py`/`worker.py`
   but is not exposed by `server.py`'s HTTP handler), so this proxy does not claim to pass settings it cannot
   actually deliver.
2. **MOSS Image Studio** is proxied to the existing MOSS Image Studio HTTP API
   (`tools/moss-image/moss_image_service.py`) over the internal k3s bridge (`http://10.242.0.1:8791` by default),
   same-origin/no-auth, exactly as MOSS's own page already calls it. `MossClient` only forwards an explicit
   allow-list of paths MOSS already exposes (`/api/presets`, `/api/status`, `/api/config`, `/api/gallery`,
   `/api/generate`, `/api/session/start`, `/api/session/end`, `/api/jobs/<id>`, `/api/jobs/<id>/cancel`,
   `/api/images/<name>.png`) — it never reimplements MOSS's own GPU session handling.
3. **Mesh** generation is proxied to the real call path
   (`ansible/roles/llm-model-lab/files/opencode_mesh_bridge.py`), a root-owned Unix socket that checks the
   connecting process's real UID via `SO_PEERCRED` against an allow-list — the primary allowed UID
   (`llm_mesh_bridge_uid`, 1009) plus `llm_mesh_bridge_additional_uids` (`ansible/roles/llm-model-lab`).
   Creation Studio runs as a dedicated, non-root system user (`creation_studio_uid`, 1013 by default) that was
   deliberately added to that allow-list (an operator-approved access-control change, 2026-11-19 — not something
   this service grants itself) and carries the shared supplementary group (`creation_studio_mesh_bridge_gid`,
   1009) needed to traverse the socket's directory and read the Model Manager password file. `MeshClient` speaks
   the bridge's own wire protocol directly (one JSON object + newline request over the Unix socket, one
   `{"ok":..., "result"|"error":...}` + newline reply), using its `submit`/`list`/`status`/`retrieve` operations;
   it never reimplements the GPU pipeline. `/api/mesh/status` additionally reads the existing
   **world-readable** GPU controller observability snapshot (`observability.py`'s `watoom.gpu-observation.v1`
   schema, written mode `0644`) to show the controller's current phase/owner and whether Mesh currently owns the
   GPU. If `--mesh-bridge-socket` is empty, `/api/mesh/generate` returns a `503 mesh_not_configured` naming the
   blocker instead of silently no-opping; it never fakes a result or bypasses the bridge's UID check.

4. **GLB 3D Coder** (2026-11-19) sends a chat completion for `ccore/Qwen3.5-4B-GLB-3D-Coder` (Q8_0, router model id
   `glb-3d-coder`, `manifests/10-infrastructure/llm/llama-cpp-qwen35-glb-3d-coder.yml`) to the **existing LLM router**
   (`--glb-router-base`, its ClusterIP); the router asks the GPU controller for the switch, nothing GPU-side is
   reimplemented. Everything follows the model card: its system prompt, its sampling (temperature 0.8, top-k 40,
   top-p 0.95, min-p 0, repeat penalty 1.0), thinking on and no `max_tokens` (answers average ~20K tokens). `GlbCoder`
   runs one job at a time (the server has one slot) and streams the answer in a background thread, so the page only
   polls `/api/glb/job`; `/api/glb/cancel` closes the stream. The page's dropdown holds the card's 25 "Domains and
   prompt ideas" plus its 6 gallery prompts (`/api/glb/config`); picking one fills the prompt box for editing. The
   generated HTML is served by `/api/glb/page` under a CSP **sandbox without allow-same-origin** (scripts, downloads
   and the Three.js CDNs only), shown in a sandboxed iframe whose own Export GLB button saves the `.glb`. Finished pages
   and job records are kept in `--glb-output-dir` (`/data/ai/creation-studio/glb-3d-coder`) and reloaded on restart.

   **Model (2026-11-20, T-0103):** `creation_studio_glb_model` is `mm-2549a44c036d0811`, the
   `prithivMLmods/Qwen3.5-4B-GLB-3D-Coder-MTP-Repacked` Q8_0 (a repack of ccore's fine-tune with an MTP head),
   installed through Model Manager with `draft-mtp` and 2 drafts (the card's `--spec-draft-n-max 2`) and thinking on.
   Measured with the studio's exact request (chest prompt): 112 tok/s, 43% of drafts accepted. ccore Q8_0 (`mm-1664`)
   ran at 101 tok/s and stays installed as the fallback. The BF16 repack with MTP ran at 79 tok/s, so it was not used.

   **Page check (T-0103).** The 4B model sometimes writes JavaScript that never runs (2026-11-19 sword: a named import
   that `RoomEnvironment.js` does not export, then a use-before-declaration), so the preview is a blank viewport. The
   preview (never the download) gets `GLB_ERROR_REPORTER` as the first script in `<head>`: it shows the page's own
   `error`/`unhandledrejection` text on the page and posts it to the studio, and 4 s after `load` it posts a health
   check (3D canvas size, an Export GLB button). The studio shows the result as "Page check" in the run summary; no
   answer within 25 s means the page is frozen or still loading. A main-thread hang cannot be caught from inside the
   page, only timed out.

## Repair, revise and the prompt builder (T-0103)

- **Repair / Revise with the model** (`POST /api/glb/repair {id, error?, notes?}`, at least one of the two): a new run
  of the same model with the system prompt, the original request, its own page as the previous answer, then the page
  check's error and/or the owner's notes on what the render shows, ending with a request for the complete corrected
  file. The run keeps `repair_of`, `repair_error` and `repair_notes`; *Recent* marks it "↻ revision of". The card
  expects "a retry or a small code correction", and its showcase assets went through a validation harness. Measured
  2026-11-20: the sword repair fixed the reported import error (10.8K tokens, 2 min 48 s), and the next error then
  showed up further down the page. A notes revision of the chest ("end walls missing") introduced a new error, which a
  repair then fixes. Expect a short chain of runs.
- **Missing walls or sides** are geometry the model never built (checked from five camera angles: the chest's end
  walls were a frame and one or two boards). No error check sees that, so the notes box exists.
- **Prompt builder**: generic for any asset. The card's structure for detailed requests: main object first, then
  components, colours, materials, placement, movement (static when empty), style. An optional, default-on line asks
  for closed, solid geometry visible from all sides with every part attached.
- **Configuration verified 2026-11-20:** the live chat template is the GGUF's embedded one, byte-identical to
  `chat_template.jinja` in both the repack and ccore repositories. The repack's GGUFs (2026-11-05 10:05) were built
  from ccore's re-released checkpoint u008186 (05:42 the same day), so the card's "re-download if before November 5"
  does not apply. Sampling, unlimited thinking and output follow the card.

## Page information (T-0103)

- **GPU strip** under the header (every 5 s, from `/api/glb/gpu`, `/api/mesh/status`, `/api/moss/status`): what holds
  the GPU (router model name, MOSS session or LLaMA-Mesh), the controller phase/owner, and what Generate would do in
  each section. MOSS can only start a session while the primary model is loaded (`qwen-ready`), so the strip says so
  when another model is loaded.
- **GLB progress**: elapsed time, tokens so far (characters / 3.3, measured on two runs), live tok/s, a time-left
  estimate against the card's ~20K-token average, and a progress bar.
- **GLB run summary**: model, total time, time before the first token, tokens, speed, finish reason (`length` means the
  page is cut off) and the page check. *Recent* rows show each run's time and tokens. *Collapse* hides the preview
  and summary again.
- **"How this section works"** in every section: what it makes, how it runs and takes the GPU, measured times and
  where the output is kept.

## Where things are on the server

Nothing is installed or started unless `creation_studio_enabled` is set true (see
`ansible/roles/creation-studio/defaults/main.yml`), same policy as `moss-image`. The normal entry point is
`ansible-playbook ansible/playbooks/creation-studio.yml -e creation_studio_enabled=true`.
