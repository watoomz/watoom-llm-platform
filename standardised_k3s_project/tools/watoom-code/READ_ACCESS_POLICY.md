# Critic and investigator evidence access

Critic challenges diagnoses/plans; investigator answers missing factual questions. Both can read/search any relevant exposed server path. The app exposes `/data/ai` and `/data/github` read-only, with existing approved project write mounts retained for builders. No host-root, SSH credential or OS privilege bypass was added.

Native role permissions allow read/glob/grep, skill/catalogue search, web search, questions and memory recall. Reads are permitted without owner approval; redact credentials from evidence and outputs. Common read-only shell commands run without approval for all agents. A complete-invocation classifier and exact native tool-call binding authorize this subset through the permission evaluation hook. Commands outside the subset retain their existing policy; critic/investigator diagnostics outside it use native ask, then the same agent executes the approved command and continues. Rejection stops the operation. No automatic blanket shell grants are made. The agents remain non-modifying: write/edit, worker generation, engine launches and ownership/provenance bypasses remain denied. An approved diagnostic does not authorize repairs or privileged access setup.

Authoritative roles: `ansible/roles/opencode-agent/files/v2-native/agents/watoom-{critic,investigator}.md`. Guard source: `ansible/roles/watoom-code/files/coordinator-guard/index.js`. Scoped deployment: `ansible/playbooks/watoom-code-read-access.yml`, only under the native idle release fence. The durable resources template carries the repository mount; scoped activation patches only that mount and managed policies rather than applying unrelated resources.

Validation: `tools/watoom-code/test-read-access.mjs`, full coordinator guard regression and review schema checks. The existing native core permission suite passed 104 tests, including permission replies and command-scoped saved grants. Live roles, immutable guard and repository mount were verified before resuming the same existing job. Hourly monitor was deleted at owner request.

## Native tool selection
All managed roles carry the same native-first decision rules near the start of their system instructions: read exact files, glob filenames, grep content, search/load catalogue instructions, and use verified worker operations for execution. Shell reads are an approved alternative, although native Read remains preferred. Broader commands retain native approval where their role requires it. Pending approval, actual rejection, missing file, truncation and no-match are distinct outcomes; a pending prompt is not a filesystem denial. A readable receipt must not trigger shell approval just because the model chose cat.

The classifier checks the full command before shell parsing can discard redirects. No blanket `cat *`/`rg *` grant is used: output redirection, chaining, substitutions, executable rg preprocessors, unknown executables and long-running tail followers are not auto-approved. Exact session/message/tool-call/agent binding is removed after execution, preventing stale or cross-agent reuse. Existing engine, ownership, visual and role guards run before execution.

## Retained admission lease recovery
`recover-idle-admission.py --evidence <new-private-directory> --i-approve` is a root operator recovery, not an agent capability. It requires no active sessions, zero durable pending inputs/claims/background or specialist work, and no GPU ownership/inference leases. The existing maintenance ingress fence closes admission; the old app is stopped, durable clearance is checked again, and an owned persistent native fence is created before a replacement starts. It never clears a live lease counter, alters receipts or deletes pending inputs. Database backup and owner evidence remain private. On partial activation the owned native fence remains held for operator recovery. Normal deployment continues to use the native idle guard; this controlled retirement is for an idle process with orphaned in-memory admissions.

Checksum reads/checks are approval-free for all roles: `sha256sum`, `sha1sum`, `sha224sum`, `sha384sum`, `sha512sum`, `md5sum`, `b2sum`, and `cksum`, including check/verification options supported by the installed utility. A mismatch is a real nonzero result; do not hide it or rewrite expected hashes. Writing a checksum manifest is a modification and retains its existing permission policy. Read-only checksum access to existing worker protocol files does not permit changing runtime-owned requests/status or bypassing pixel review.
