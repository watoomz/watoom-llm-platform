# Native bounded game worker
The versioned native guard registers watoom_game_worker for coordinator/builder requests and status. Read-only roles have no launcher. Typed operations: regression/import/capture; no arbitrary commands, filesystem paths, memory tuning or model/GPU changes. Project must equal the native session location and configured game allowlist.

Root dispatch requires the matching completed native tool call/message/metadata and request identity, so project-written request files alone cannot launch work. It reuses existing game_validation.py/game_import.py/game_capture.py with fixed resource ceilings and headroom checks. Source fingerprints guard dispatch/delivery; the full regression receipt includes its actual source manifest. One root lock serializes workers. Existing Godot units and deployment fences defer dispatch. Duplicate requests for the same operation/revision reuse the existing identity/result. No repeated failed runs without source changes.

Root-owned public status files are atomically published without following project symlinks; native status rejects app-forged files. Actual receipts are app-readable; raw operator logs remain private. Completion resumes the same existing coordinator. Pending work waits30s polling without model calls. Game capture currently targets the explicitly maintained P6 scene. Before an explicit owner stop, the operator must reconcile/cancel any queued worker requests; do not resume stopped projects through health monitoring.

When RAM is insufficient and all native sessions are idle, the dispatcher acquires controller ownership as the verified game-worker service. The controller checks inference leases and actual backend idleness, parks the primary without starting another model, and restores/verifies the same primary before notifying the coordinator. The 3GiB worker plus 2GiB reserve remains mandatory. ExecStopPost reconciles a dead worker owner; uncertain outcomes never bypass controller fences.

The fixed operation poo-vfx-inspect invokes tools/fab/inspect-poo-vfx.py for the owner-approved source only. It reuses the approved bounded UE job template and installed runtime. No caller-defined assets, script, path, engine flags or shell are accepted. It scans actual classes and loads up to3 non-demo assets per supported class (NiagaraSystem/Material/MaterialInstanceConstant/Texture2D/StaticMesh), confirms source hashes unchanged and publishes operator-unreal receipts. Inspection is explicitly distinct from export/playback/Godot acceptance. Read-only roles cannot launch it; their execution-authorized coordinator/builder requests it. Direct specialist availability is now stated from the actual enabled context, separately from Code Mode discovery, without changing guards.

Capture routing is explicit: capture=P6 terrain; capture-p7=P7 ability runner. tools/watoom-code/capture_profiles.py fixes scene and exact output filenames; arbitrary scene paths are not accepted. Both runner source pairs are fingerprinted. Capture receipts include profile/scene and require all3(P6) or8(P7) fresh files plus no runtime errors; job IDs never choose scenes.

P7 capture rejects an all-eight-byte-identical PNG set as P7_FRAME_EVIDENCE_IDENTICAL. This does not substitute for independent visual review; differing bytes alone do not prove ability fidelity. P6 behaviour is unchanged.

Cache mount preparation is shared by import/capture and refuses symlinks, preserving existing data. Exit226/NAMESPACE is classified as pre-engine startup failure. Native shell guard blocks full Godot editor/import in app while permitting parse-only checks. Fingerprint cache-mount-v1 binds requests to the corrected worker contract; no terminal job is reset/replayed.

Import diagnostics: retain the bounded systemd unit journal in unit-journal.log and include failure_reason plus the last 40 log lines in the app-readable receipt. A systemd-run exit 1 with empty Godot errors is not evidence of an engine defect; inspect the unit journal for OOM/namespace failures before retry. The 2026-10-23 cache import reached 3 GiB and was OOM-killed; do not repeat unchanged.

The typed operation godot-game runs fixed watoom-godot-game skill steps (gg_project, gg_style, gg_terrain, gg_water, gg_light, gg_catalog, gg_scatter, gg_census, gg_player, gg_export, gg_ui, gg_assets check; the list is STEPS in tools/watoom-code/godot_game_spec.py) against a staged scratch copy of the game under .opencode/tmp/, on the Bazzite worker only (never the homelab server; no local fallback). Request: .opencode/godot-game-jobs/<job>/request.json (schema:1, project_dir, steps of {script, sub, args}, optional deadline_sec 120-1800, memory_gib 3-8). Args are plain tokens: no paths, quotes or shell characters, and the worker adds --project itself, so a step cannot reach outside the copy. game_godot_game.py runs it in rootless podman (no network, read-only root, no GPU, Mesa llvmpipe, the pinned Godot at /godot, the installed skill read-only at /skills) through godot_game_driver.py: the verify-loop selftest for gl_compatibility first, then each step, stopping at the first failure. Only the low-poly and pixel-art styles can run (the Vulkan styles need a GPU; the spec refuses them). Results come back to .opencode/godot-game-out/<job>/project/ (files over 100 MB skipped, .godot/ and gg_data/jobs/ omitted) with a per-step receipt (exit code, seconds, log tail) in result.json; the live project and the staged copy are never changed, and the receipt records whether the staged copy changed during the run. The Bazzite capture image (localhost/watoom-toolkit-xvfb, Fedora 44) already provides python3 3.14, numpy 2.4.6, Pillow 12.3.0 and Xvfb (checked 2026-11-17), so no image change is needed; the operator still probes for numpy and Pillow first and reports NOT_STARTED if they ever disappear.
