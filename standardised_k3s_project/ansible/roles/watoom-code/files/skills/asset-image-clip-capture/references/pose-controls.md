# Verified pose preparation

Read only for a requested pose change. Obtain actual worker `inventory.json` first unless a matching current rig record exists. Armature rows expose `bone_count`, `pose_bones` (up to1024; use count to detect truncation), `controls`, `drivers` and widget names. Each pose-bone row includes name, parent, deform flag, rotation mode/Euler, location, head/tail, rest matrix, rotation locks and constraints with target/subtarget/influence/mute. Controls/non-deform flags are candidates, not proof of an IK/FK control path. Parse just the selected armature's relevant records with ordinary JSON tools; do not launch bpy or scan unrelated assets in the app.

1. Translate the user's pose into body segments, gaze, support/contact and framing criteria. Use the observed hierarchy, axes/rest transforms and rig documentation to select verified controls. Preserve the authored skeleton, mesh binding and outfit. Never guess DEF/MCH names or apply another character's numbers.
2. If an observed existing Action/frame already matches, select its actual owner/Action/frame. Otherwise use `pose:[{armature:"actual object",bone:"actual pose bone",rotation_euler:[x,y,z]}]`. Values are XYZ radians within +/-pi; max128 entries. The worker sets the frame/evaluates animation **before** applying explicit pose rotations, then updates the rig. The same order is used for each rendered frame. Requested rotations are keyed only in an in-memory copy of the active Action (or a new working Action), so render-time animation evaluation cannot silently restore the old channels. Originals on disk remain unchanged. Channels are verified again after each render. Existing Action channels remain for other controls; explicit rotations are absolute channel overrides, not animation generation.
3. Use the supported FK/control path. Inventory constraint influence/driver paths/locks matters: an IK target needing translation, custom FK/IK switch, bone scale, prop creation or new constraint cannot be expressed by the current rotation-only adapter. An ordinary rotation may be anatomically wrong even if a bone moves. Do not disable constraints/drivers or edit protected sources to force it; return POSE_ADAPTER_BLOCKED naming the exact missing operation. Existing clothing MASK toggles are separately supported.
4. Use a small fully clothed preview. `pose-evidence.json` records requested, pre-edit and actual channel rotations, frame, and number of evaluated deform bones changed. Overridden channels or a changed request producing no evaluated deform-bone movement fail before rendering. Matching channels/deform movement prove only execution, not natural anatomy, contact, framing or the semantic pose. Review the PNG for all of those. Driver-driven shape-key-only poses may need a separate qualified adapter; do not claim them proven by bone evidence.
5. If a preview has a concrete defect, make one targeted new revision, preserving its predecessor. Stop repeating an unsupported operation or unchanged failure. Save the per-asset control mapping, source/dependency identities, pose plan, actual evidence and accepted image in a scoped recipe only after visual review.

A fresh standing A-pose cannot fulfill a requested seated pose. Camera motion is not skeletal motion. Looking at the user prompt or an image hash is not pose validation.
