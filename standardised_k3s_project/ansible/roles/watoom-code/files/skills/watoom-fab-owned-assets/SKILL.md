# Owned Fab acquisition
Read the current server catalog `/data/ai/assets/catalog/fab-owned.json` (629 entries at initial refresh; current count/timestamp authoritative). Search titles/types selectively, not the whole catalog in every prompt. Owned inventory is separate from downloaded files and validated project derivatives. Never buy or claim ownership beyond the catalog. Preferred stylised packs remain candidates even if conversion is pending.

1. Select bounded relevant exact IDs and explain fit, intended project, source formats where known, estimated size if known (otherwise unknown), dependencies/conversion route and preparation plan. Reconcile existing local source/receipts before requesting duplicate downloads. No library-wide automatic acquisition.
2. Write one request per asset under `<project>/.opencode/asset-requests/<request-id>.json`: schema1, project absolute path, asset_id, title, reason, preparation_plan, status AWAITING_OWNER_APPROVAL, session_id (existing project coordinator). The operator helper `tools/fab/owned_catalog.py request` can create a canonical hashed request. Agents may write requests with native write if the operator helper is unavailable in their tool boundary.
3. Ask the actual owner through the native question tool, showing exact asset/title, project, known size and preparation scope. Wait for an explicit approval. Project/task approval, owned status or this skill is NOT approval to download. Never fabricate owner approval or approve your own request. Continue independent work while waiting.
4. The maintained root-owned approval timer polls these requests and completed native question answers in the SAME coordinator session. Compute the canonical request SHA256 with sorted JSON keys and compact separators (or use the helper). Ask exactly one native question containing `FAB_APPROVAL:<request_hash>`, exact asset_id, exact project path, title/reason/preparation plan; use options labelled `Approve download` and `Decline`. Only the actual completed native answer `Approve download` authorizes fulfillment. Do not offer the approval option as an automatic default or interpret silence/freeform ambiguity as consent. Approval binds the immutable request, project and owned asset. Agent prose cannot authorize the downloader. The worker reuses the existing authenticated downloader and Catalog, publishes a project receipt, then resumes this same coordinator for preparation. Do not claim running until a real status/receipt exists; continue independent work while pending. If declined, do not resubmit unchanged.
5. Operator fulfillment uses the existing authenticated server client, downloader checksums/resource bounds and existing Toolkit index; no desktop storage or new service. Read the project `.receipt.json`. Partial/failed downloads retain evidence; reconcile, never start duplicates. Unsupported MetaHuman formats/conversion paths remain explicit gaps; do not trigger desktop downloads without owner permission.
6. SOURCE_INDEXED_PREPARATION_PENDING is not READY. Use indexed source refs through supported Toolkit operations. Inspect licences and dependency closure; preserve purchased originals. Stage derivatives in project/generated paths, retain material/texture relationships, meshes, applicable rigs/clips/LOD/collision; prefer installed EL4CTEO for Blender. Use an actually supported Unreal conversion when needed, never infer it from installed runtime alone. Import through bounded external Godot worker; collect real import/load/runtime and independent visual receipts. Do not execute downloaded plugins/code automatically. Publish engine-ready status only for the exact validated derivatives and report remaining gaps honestly.

For cross-pipeline discovery run `python3 /config/skills/watoom-fab-owned-assets/scripts/asset_advisor.py advise "<query or asset id>" [--category <category>] [--json]` (or read `/data/ai/assets/catalog/asset-index.md`) BEFORE choosing an asset. Follow the recommended pipeline, its format/rig preconditions, concrete tools and pitfalls; candidates are not qualified integrations until validated for the exact source and target. Use `python3 /config/skills/watoom-fab-owned-assets/scripts/request.py --project <root> --session-id <coordinator> --asset-id <id> --reason <reason> --preparation-plan <plan>` where native shell is allowed. It creates the canonical request and returns exact native question input; no downloads or approval occur. Read-only roles return a proposal to the coordinator instead of executing this script.

## Format and version preflight before downloading
Before requesting approval or acquisition, inspect the actual Fab listing/download metadata for all offered formats and engine versions. Match the target project and asset type: prefer an existing compatible native Godot package for Godot, a complete portable GLB/glTF/FBX with textures/rig/animation when it preserves the required features, or native Unreal when Blueprint/Niagara/Geometry Script behaviour is needed or no faithful portable option exists. A format is not automatically best just because it is portable. Verify dependency completeness, material/shader fidelity, animation/rig support, compatible version and the supported download/conversion route; do not infer offered formats from the UE-only account client. Record unavailable/unknown options honestly. Include available formats, selected format/version, project target, evidence source and rationale in the owner approval request. Never silently substitute an Unreal download for a selected portable format or fetch all formats. Previously completed downloads need no automatic duplicate download; evaluate a better source first and obtain approval for an additional acquisition.

New requests require a `format_selection` object with `target_engine`, `available_formats`, `selected_format`, `source_evidence`, `rationale`, `engine_version`. The exact JSON is included in the native approval question and bound to its request hash. Only Unreal Engine is currently handled by the authenticated epic-fab downloader; another selected format requires a separately verified supported route and must not silently fall back. For UE select an actually offered version compatible with the installed target runtime; use the client version-resolution evidence, never presume latest is best.

## Portable export of downloaded Unreal packs (operator)
`scripts/unreal-export/export_pack.py` exports skeletal meshes and animations to GLB (Unreal glTF Exporter; the FBX skeletal exporter needs a render device the headless worker lacks), static meshes to FBX and textures to TGA, from a pack under `/data/ai/assets/fab/<pack>` into a new `/data/ai/artifacts/unreal-export/<name>`. It runs `scripts/unreal-export/ue_export_assets.py` inside the pinned engine in a bounded unprivileged worker with the pack mounted read-only, verifies the source hashes are unchanged and writes `result.json` (its `backend` field says where it ran). `--backend auto` (default) runs on the Bazzite worker when its runtime is staged and it has the RAM and disk, keeping big exports off the homelab server: the pack's Content is synced to Bazzite's cache and verified file by file, the export runs in rootless podman with no network, and results are pulled back into `--out`. Otherwise, or with `--backend local`, it runs as a k8s Job on the homelab (default 4 GiB). It falls back only before the worker starts; a started export is never replayed. `scripts/unreal-export/bazzite.py check` shows Bazzite's free RAM/disk and staged runtime; `bazzite.py stage-runtime` (operator, one-time or after an engine/toolkit change) copies the slimmed runtime (`unreal-runtime-exclude.txt`) and the toolkit image. It needs root and kubectl, so agents never run it directly. From a game project session, request it through the native game worker instead: write `.opencode/unreal-export-jobs/<job>/request.json` as `{"schema":1,"pack":"<folder under /data/ai/assets/fab>","root":"/Game/<Folder>","classes":["SkeletalMesh","AnimSequence"],"include":["<name fragment>"]}` (optional `exclude` list, default `/Demo/`, `/Maps/` and `/Levels/`; `max_assets` 1-2000, default 400; `memory_gib` 2-12, default 4), then call `watoom_game_worker` with `operation:"unreal-export"` and the same `job`. The dispatcher validates the manifest (a FAILED status names the bad field), runs this script with `--backend auto`, and copies the exported files into `.opencode/unreal-exports/<job>/`; the receipt lists each file with its Unreal class and path. `PARTIAL` means some assets failed (see `errors`). Each job name is used once; edit the manifest and use a new job name to retry. Submit only your own current job: names you wrote a manifest for in this session, never another session's, another project's or an old job. `status` takes the job NAME you requested, never the 64-hex request_id. A FAILED, STALE_REQUEST or RECONCILIATION_REQUIRED job is finished and is never re-run: its status says where to read the failure (the manifest field named in `reason`, or `worker_result.failure_reason`), fix it and submit under a new job name; a failed job is a result to fix, not a blocker. QUEUED means wait (Bazzite may be busy or offline; the status shows the age): do not resubmit or poll in a loop, and report a job queued over 30 minutes to the operator. Ask for one pack folder per job and keep `max_assets` small. `root` is `/Game/` plus a folder inside the pack's `Content/` (for example `Content/AnimalsPack` becomes `/Game/AnimalsPack`). Exported GLBs feed `sims4-animation` `retarget-any.md` (Blender source kind) and the Blender/Godot pipelines.

For reading a Blueprint-only pack's tuning data as plain JSON (e.g. the Hyper Combat Framework's DT_Firearms/DT_Combat/DT_ApplyEffects,
mined as content-source-only reference per T-0063/T-0065 -- never run its Blueprint code), call `export_pack.py` directly with
`--script ue_export_datatables.py` (operator/root only, not yet wired into the game-worker manifest): it dumps every DataTable under
`--root` to one JSON file per table under `exported/`, same sandboxing and source-hash verification as the asset export.

## Rebinding textures onto an exported glb (T-0067)
`export_pack.py`'s exported meshes (`.glb`) and textures (`.tga`) are separate files, and the glb's material slots lose
their Unreal material name on glTF export (renamed `Material_0`, `Material_1`, ...), so nothing rebinds the textures
onto them -- an imported combat mesh shows a flat white albedo in `gg_assets.py check` until this is run. `scripts/
unreal-export/rebind_textures.py --glb IN.glb --textures-dir <exported textures folder> --bind '{"Material_0":
"Exterior","Material_1":"Interior"}' --out OUT.glb` drives headless Blender (`_rebind_worker.py`, same tool this
repo already uses for mesh/material work -- see `tools/blender-asset-builder`) to wire each named group's `T_<group>_
D|BaseColor` (albedo, required), `_normal`, `_roughness`/`_metallic` or packed `_ORM`, and `_opacity` files onto that
material's Principled BSDF, then re-exports the whole glb with the images packed in. `--bind`'s material names must be
read from the glb first (e.g. a one-off Blender import + list materials/poly-counts-per-slot) since names are generic
and group assignment can't be inferred automatically. An `_emissive`/`_emiss` file, if present, is intentionally left
unbound: `gg_assets.py check` (`gg_catalog.py`'s `glows` rule) flags any non-zero `emission_energy_multiplier`
regardless of how dark a masked emissive texture mostly is, so wiring one trips a false error. Verify with `gg_assets.py
use --replace --allow-large` (rebound glbs with packed textures run well past the normal 30 MB limit) then `gg_assets.py
check` on the project slot.

## Non-Unreal items (FBX/GLB/OBJ) and the rig vault
The downloader above only fetches Unreal packs. A non-UE item is registered with `epic-fab extras add <listing uuid> "note"` (uuid from `epic-fab search`), the owner downloads the format in the Epic launcher on the rig, and `tools/fab/rig_vault_fetch.py list|copy` copies it from the rig vault (`...\\VaultCache\\FabLibrary\\<Title>-<uuid8>`) to `/data/ai/assets/fab-library-extras/`. Import and placement are in `watoom-texture-layering` (`references/unreal-scene.md`, section "Fab downloads that are not Unreal packs, and placing imported meshes").
