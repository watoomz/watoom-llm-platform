# Verified recipe selection
The general workflow is asset-image-clip-capture references/generic-capture.md. No prior receipt is required. When a selected project receipt or specific AgentMemory record is available, use it as optional scoped evidence; otherwise continue with the general inventory/preparation procedure. Do not scan the library or query models repeatedly.

A reusable preparation recipe must identify the actual source asset/hash, a preserved prepared derivative/hash, dependency mapping/hashes, compatible executable/profile, worker request contract, resource limits, output/receipt paths and real successful exit. Verify the selected derivative/dependencies still exist and match. A task title, installed skill, different asset's receipt, old queue entry or current pod readiness is not matching success.

Reuse only matching preparation stages. Reuse process/lighting/capture setup where relevant; create fresh output paths and receipts for the new requested image/clip. Prior image acceptance never accepts a new pose or framing. A turntable is not skeletal animation. Source rig/action requirements remain explicit.

If source format needs a newer runtime than a pinned skill supports, select only an already verified compatible worker/profile with the required interface. Record the specific mismatch and stop that unsupported stage once. Do not downgrade/compress/strip sources, install another engine, route through Unreal, restart services or repeatedly try the same failing runtime as an implicit fallback.

Select capabilities by supported operation and deployed schema, not by the character's name or source folder: an existing-asset capture is not image generation or character generation. Use asset-image-clip-capture for capture, relevant installed Blender modules for an authorized edit, and watoom-blender-asset-builder for a supported full asset build. Fixed game capture profiles cannot render arbitrary scenes. Worker operation names and native capability IDs are different. Read actual discovery once and retain the descriptor in the coordinator checkpoint.

For an uncertain existing job, reconcile its stable identity/receipt before submitting anything. A failure or missing mount in the app does not prove a worker runtime is absent. Read-only investigators/reviewers return evidence; they cannot launch execution jobs. An execution-authorized builder uses the approved bounded worker, not a heavy process in the application shell. If none supports the operation, save a concrete request and report the precise gap without pretending the staged runner is deployed.
