# Unreal plan (Blueprints first, UE 5.8 on the rig)

One task = one row; give a model **one phase at a time**. Agents are in `agents.md`. `UE` below means the `watoom-ue`
MCP tool (when listed): `tools(action="call", category=<c>, method=<m>, args={...})`, written here as `category.method`.
Before the first use of any action: `wlk_symbol` for its card (product `ue-mcp`; route rules in `watoom-ue-route`) and
`tools(action="describe", category, method)` for the exact parameters. The editor must be open on the rig and the
route enabled; check with `project.get_status` (`editorConnected: true`). If the route is not listed or not connected,
say so and stop: do not invent a workaround.

Honest limits (2026-11-14): the route has not yet run a full game build end to end. The rig has **no Windows SDK**, so
plan for **Blueprint-only**; `project.write_cpp_file` / `editor.build_all` are allowed by policy but cannot compile until
the operator installs the C++ toolchain. A modal dialog in the editor blocks every action (`dialogBlocking`): report it.
Asset packs are staged on the lab at `/data/ai/projects/games/ue-staging/<pack>/` and reach the rig as
`P:\games\ue-staging\<pack>\`; copying them into the project's `Content` is an operator/rig-side step.

## Verified recipe and gotchas (landscape from a lat/long terrain, 2026-11-14)
Run order that worked end to end (505x505 vertices, 4 km, 5 layers):
1. `watoom-terrain-map` -> `layer_masks.py` (set `"smooth_m": 20` on gentle ground) -> `unreal_landscape_export.py heightmap` and `weights --vertices 505 --tile 127`.
2. Stage `heightmap16.png` under `/data/ai/projects/games/ue-staging/<name>/`; the editor reads it as `P:\games\ue-staging\<name>\heightmap16.png`.
3. `landscape.plan_real_world` (gives the create scale and location), `level.create` (it also loads the new level; there is no `level.open`), `landscape.create` with those values, `landscape.import_heightmap` (png16, `space: quad`, `minHeight`/`maxHeight` = the plan's minWorldZ/maxWorldZ), `landscape.add_layer` per layer, then `landscape.set_layer_weight_region` per tile (inline `weightsBase64`, write every layer).
4. Verify by reading back: `landscape.get_height_region` correlates 1.0 with the source (orientation needs no flip) and `get_layer_weight_region` is byte-identical.
5. Textures: stage the jpgs and `asset.import_texture_batch` (items `{filePath, preset: "color", maxTextureSize}`, `packagePath`, `save: true`).
6. Material: `material.create`, then `material.build_graph` with TextureCoordinate, TextureSample (`texturePath`), `MaterialExpressionLandscapeLayerSample`, Multiply, Add; then `landscape.set_material`.
   **Set the layer name with `"properties": {"ParameterName": "<layer>"}`.** The plain `parameterName` field is silently ignored for this node class (the node reads `'None'`, no layer drives the colour). Always read the graph back (`material.read_graph`) and confirm each `Landscape Layer Sample '<layer>'`. `clearExisting` is not a `build_graph` parameter; to redo a material create a new asset.
7. The landscape actor's origin is its corner: it spans 0..size*100 cm in X and Y, so the middle is (size*50, size*50). The editor viewport camera starts near the origin, usually under the terrain, so the picture is black until `editor.set_viewport` moves it (e.g. location (size*50, -size*30, 70000), rotation pitch -22, yaw 90).
8. Seeing the result (one rule, details in `watoom-texture-layering/references/unreal-scene.md` "Seeing the scene"): `tools/rig-ue-mcp/ue_viewport_shot.py OUT.png [--camera X Y Z PITCH YAW]` for lighting, materials, post-process and colour (it calls `editor.capture_screenshot`, which writes its file on the rig asynchronously and does not return an inline image, lifts the editor's CPU throttle while it captures, and pulls the PNG back); `editor.capture_scene_png` only for geometry and placement. Always look at the image; a successful call is not a visual check.

9. **Save and reload the level after assigning the landscape material (reload = open another level with `editor.open_asset`, then this one; reopening the same path does nothing).** Until then the components keep drawing the default grey grid (Base Color, Unlit and Lit all look uniform grey, even for a flat red test material) although the property, graph, layer infos and shaders all check out. What makes the layers appear: `asset.save_all_dirty {saveMapPackages:true, saveContentPackages:true}`, `level.load` another map, `level.load` this map, then wait for `editor.get_shader_compile_status {waitUntilIdle:true}`; check `editor.get_log` for `Failed to compile Material` first, because a failed compile keeps the last good shader. A property-setter re-assignment does not.
10. Helper for steps 6 and 9: `watoom-texture-layering/scripts/unreal_landscape_material.py --layers <layer_masks out> --textures <layer>=/Game/... --material /Game/.../M_Terrain --landscape <landscape label> --tiling 2.5 --out material_calls.json` (landscape UVs are one unit per quad, so tiling is `quad_m / tile_m`, about 1.5 to 3) writes the exact `material.create`, `material.build_graph`, `landscape.set_material`, save and reload calls plus the checks.
11. **Opening a level:** `level.create` on an existing path only reloads when that level is already the open one; from another level it reports `existed: true` and loads nothing. Use `editor.open_asset {assetPath: "/Game/Maps/<level>"}` to switch levels, then re-aim the camera.
12. **Scenery (verified):** staged packs are copied into `Content` by the rig, then `asset.list`/`asset.search` give real paths (pack folders can nest, e.g. Wildwood grass is `.../Grass/Grass/Grass/Meshes/SM_Grass_01`). Foliage: `foliage.create_type {meshPath, name, packagePath, onConflict:"skip"}`, `foliage.add_type_to_level`, then `foliage.add_instances {foliageTypePath, center, radius, count, seed}` (traces onto the landscape; ~800 calls in batches of 25 filled a 4 km map with trees, bushes, flowers, boulders). Choose sites from the terrain masks (flat for villages, slope for rocks, grass weight for forest). Removing a type with instances needs `force: true`.
13. **Look-out for black foliage:** packs whose grass material uses landscape ground projection (Wildwood `SM_Grass_01`) render black on a custom landscape. Swap to clover, plant or leaf-field meshes. Check every new foliage type in a capture.
14. **Terrain colour:** self-made brown jpgs gave a sandy map. Pack terrain textures (`Fantastic_Village_Pack/textures/T_ENV_TERRAIN_*_BC`) gave a green map; build the material with `unreal_landscape_material.py` and assign it by the landscape's **label** (`ZAS_Landscape`). Prefabs: `level.place_actor {actorClass: "<bp path>.<bp>_C"}` for village houses, `level.spawn_skeletal_mesh_actor` for characters; compute ground z from the heightmap (`3694.9 + h * range`) instead of guessing.
15. **Creeks and dense scenery:** `watoom-texture-layering/scripts/unreal_creeks.py` (flow accumulation finds the lowest lines, carves the heights, lays water ribbons with a pack water material) then `unreal_scene_scatter.py` (grass grid over the grass mask, forest, bushes, rocks, village; avoids the creek). Order: creeks, then scenery. Trees need `AlignToNormal` false; test grass at eye level. Details and the card list: `watoom-texture-layering/references/unreal-scene.md`.
16. **Stale captures:** if a capture is identical after the camera moved, the viewport is not repainting (or the editor is CPU-throttled because it is not the foreground window): `editor.set_realtime {enabled: true}`, `editor.redraw_viewport`, wait, capture again; `ue_viewport_shot.py` handles the throttle itself.
17. **Playable character (verified build, UE 5.8.4):** assets under `/Game/<Project>/Player`. (a) `animation.create_blendspace_1d` (axis Speed 0-600) + `animation.add_blend_sample {animation, x}` for idle, walk, run; (b) `animation.create_anim_blueprint` on the mesh's skeleton, `blueprint.add_variable` Speed (float) and bInAir (bool), `animation.create_state_machine`, `add_state` Ground/Jump, `set_state_animation` (Ground = the blendspace), `add_transition`, `set_transition_condition {variableName, negate}`, `set_state_machine_entry`, then connect the state machine `Pose` to the AnimGraph Result with `blueprint.connect_pins {sourceNodeId, sourcePin, targetNodeId, targetPin}`; (c) enable the default `Event BlueprintUpdateAnimation` (`blueprint.set_node_property {propertyName: EnabledState, value: Enabled}`) and add TryGetPawnOwner -> GetVelocity -> VectorLength -> set Speed, then Cast To Character -> GetMovementComponent -> IsFalling (NavMovementComponent) -> set bInAir; (d) attack = `animation.create_montage` + a `AnimGraphNode_Slot` between the state machine and the Result + `PlayAnimMontage` (a cross-class variable set does not resolve through the route); (e) Enhanced Input: `gameplay.create_input_action` (Axis2D move/look, Boolean jump/attack), `create_input_mapping`, `add_imc_mapping` with keys W S A D Mouse2D SpaceBar LeftMouseButton, `set_mapping_modifiers` (W: SwizzleAxis YXZ, S: SwizzleAxis + Negate, A: Negate, Mouse2D: Negate Y); (f) the character blueprint (parent Character): Mesh with `SkeletalMeshAsset`, `AnimationMode`=AnimationBlueprint, `AnimClass` = the `_C` path, mesh at z -90 and yaw -90; SpringArm (`bUsePawnControlRotation` true, length 350) + Camera; a StaticMeshComponent attached with `parentSocket` to the weapon socket (`animation.list_sockets`); class default `bUseControllerRotationYaw` true, `bOrientRotationToMovement` false. Event graph: BeginPlay -> GetController -> Cast To PlayerController -> `K2Node_GetSubsystemFromPC` (EnhancedInputLocalPlayerSubsystem) -> AddMappingContext (set the `MappingContext` pin with `set_node_property {pinName, defaultValue}`); `K2Node_EnhancedInputAction` nodes (set `InputAction`): Move -> BreakVector2D -> AddMovementInput(GetActorForwardVector, Y) then (GetActorRightVector, X); Look -> AddControllerYawInput(X), AddControllerPitchInput(Y); Jump Started -> Jump, Completed -> StopJumping; Attack Started -> PlayAnimMontage. Place it with `level.place_actor` and `AutoPossessPlayer` Player0. Use `blueprint.add_node` with `deferCompile` and compile once; find node classes with `blueprint.search_node_types`; the route may drop a call ("daemon stopped"): read the state back and retry.
18. **Scale and ground:** `unreal_scale_fit.py` for consistent real-world size (180 cm human reference), `level.snap_actor_to_floor` after every rescale; see `watoom-texture-layering/references/unreal-scene.md`.
20. **Landscape material limits:** reload a landscape material by opening another level and then the real one (same-path reopen does nothing); keep `material.get_shader_stats referencedTextureCount` at about 8-10 or the landscape renders default grey; a macro (large-scale) colour pass must be desaturated or it greys the grass; creeks: `unreal_creeks.py --irregular --bank-paint` for deep, uneven channels with pebble, sand, mud and stone banks, water via `level.place_actors_batch` + `level.bulk_set_component_property` (material, CastShadow false), trees lining the creek via the scatter `creek_trees` phase. Details in `watoom-texture-layering/references/unreal-scene.md`.
19. **Seeing and water:** `editor.capture_scene_png` (needs `outputPath`; inline image without `warmupFrames`) is for geometry and placement only: it does not show lighting or material edits and does not draw Water-plugin water, so judge those with `ue_viewport_shot.py` (point 8); creek water = `/Game/AdvancedVillagePack/Materials/M_Inst_Water` (Wildwood `MI_River_01` renders white on planes); the ground can still read as one flat colour with a bright single grass texture, so use `unreal_landscape_material.py --macro`. Details in `watoom-texture-layering/references/unreal-scene.md`.
Debug order when the picture is wrong: read the graph back (names), flat-colour test material, then save + reload; do not assume a fault in the weights before those three.
Editor lifecycle: the editor runs on the rig as RIG\watoom; it is started by the allowlisted `WatooM-UeEditorStart` task, not by the lab. If `project.get_status` says `editorConnected: false`, ask the operator to start it. Never open the project with another engine version.

Visual acceptance needs a real capture reviewed by `watoom-reviewer`; use `watoom-engine-visual-diagnosis` when a review
disagrees with the scene. A passing compile is **not** visual acceptance.
